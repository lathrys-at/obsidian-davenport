# Davenport — Design Specification

Davenport is an Obsidian plugin. It syncs calendars in two directions over CalDAV. A davenport is a small writing desk. This davenport speaks CalDAV.

## 1. Orientation

Davenport syncs calendar events and tasks between an Obsidian vault and CalDAV servers. These servers include iCloud, Fastmail, Nextcloud, Radicale, Baïkal, Google, and other CalDAV servers. Davenport authenticates with app-passwords, or, for Google, with user-supplied OAuth credentials (§4.4). Davenport treats the calendar as a projection of the vault. The calendar owns when things happen. The vault owns what those things mean.

Five principles govern the design. Each principle recurs throughout the spec.

1. Events are records. Notes are venues. Event data lives in a plugin-owned ledger. Notes hold meaning. Notes can also receive events, but they do not have to. Many events may point at one note.
2. Sync touches only declared fields. Templates fire once at creation. After creation, the note belongs to the user. The note body is never a sync surface, except through explicitly declared channels. These channels are the description region and the attachments list.
3. The presence of data is never intent. Davenport creates or modifies a remote resource only after it receives an explicit signal. Any action that could send a message to another person always requires confirmation.
4. Ownership is declared. Ownership is not assumed. Every calendar has an explicit mode: vault-owned, remote-owned, or bidirectional. This spec states the behavior differences between the modes. It does not leave a reader to discover them.
5. Davenport demonstrates trust. Davenport does not claim trust. Unknown data survives round trips. The user can preview and pause destructive operations, and Davenport logs them. Failures are legible. Davenport never skips anything silently.

## 2. Background

### 2.1 Protocols

iCalendar (RFC 5545) is the data format. The format defines `VEVENT`, `VTODO`, and related components. These components carry properties such as `DTSTART`, `DTEND`, `RRULE`, `UID`, and `SEQUENCE`. Every calendar system speaks iCalendar or maps onto it.

CalDAV (RFC 4791) is calendaring over WebDAV. Each event is an `.ics` resource with its own URL inside a calendar collection. Discovery uses `PROPFIND` and moves from `/.well-known/caldav` to the principal, then to the calendar-home-set, then to the collections. Reads and writes use `GET`/`PUT`/`DELETE`. ETags (`If-Match`) guard these reads and writes. Queries use `REPORT`: `calendar-query` and `calendar-multiget`. `calendar-query` filters by time-range and by component. `calendar-multiget` fetches a batch of resources by URL. Change detection uses the collection CTag, which is coarse, or WebDAV-Sync (RFC 6578) sync-tokens, which are incremental. With sync-tokens, a CalDAV client sends the last token and receives the changed and deleted resources. Collections use `supported-calendar-component-set` to advertise which component types they accept. The ecosystem convention is separate collections for events and tasks. Servers with scheduling support (iTIP/iMIP) send email to the attendees when an event that carries `ATTENDEE` properties is written.

ICS subscription feeds are read-only `.ics` URLs. Clients poll these URLs again and again. Feeds have no per-item versioning and no sync tokens.

Google Calendar and Microsoft Graph offer richer REST APIs. These APIs require OAuth 2.0 with app registration. Google also requires a verification process. Neither Google Calendar nor Microsoft Graph supports app-passwords. Davenport targets CalDAV and ICS feeds only. This target includes Google, because the Google CalDAV v2 endpoint (`apidata.googleusercontent.com/caldav/v2/`) accepts OAuth 2.0 Bearer authentication. Google support therefore requires no second sync engine. Google support uses the same CalDAV engine with a different credential type (§4.4). The REST APIs stay out of scope. Rationale: one protocol covers every provider, and the engine, the records, and the conflict machinery do not depend on the authentication type.

Task silos: the Google Calendar CalDAV endpoint serves events only. Google Tasks is a separate API that permits OAuth only, and its `due` field holds a date only. Apple Reminders left CalDAV for CloudKit with iOS 13. No public API can reach the reminders on upgraded iCloud accounts. VTODO over CalDAV works with Nextcloud, Radicale, and Baïkal, and with clients such as Thunderbird and Tasks.org.

### 2.2 Platform constraints

- Network calls must use Obsidian's `requestUrl()`. Network calls must not use `fetch`. CalDAV servers do not send CORS headers. `requestUrl` bypasses CORS, and it works on mobile.
- Engine code must read the time from the clock port. Engine code must not read an ambient clock. The clock port supplies the time, and a test can control that port.
- Plugins run only while Obsidian is open. Background sync is impossible, and background notifications are impossible. This is true especially on mobile. The native calendar client on the phone is the delivery mechanism for alarms and for freshness. Davenport designs around this constraint. Davenport does not design against it.
- `data.json` (through `loadData`/`saveData`) travels across devices only when the user's sync setup carries it. There are three reasons for this limit. `data.json` is a non-markdown file in a hidden folder. Obsidian Sync gates plugin data behind configuration-sync toggles. Git setups and Syncthing setups routinely exclude `.obsidian` wholesale. Cross-device settings agreement therefore depends on the configuration. Davenport verifies this agreement at onboarding and tripwires it at runtime (§15.1). Davenport never assumes it (Appendix A item 22). `App.saveLocalStorage`/`loadLocalStorage` is official API for device-local, vault-scoped, non-synced storage. IndexedDB is available for larger device-local caches, but IndexedDB may be wiped with the app data.
- Obsidian Sync does not sync arbitrary hidden folders. Obsidian Sync syncs a non-markdown file type only when the user enables the corresponding settings toggle. Markdown files sync unconditionally under every sync method.
- Obsidian's Properties UI cannot edit nested YAML mappings. The Properties UI has no enum/select property type. There is no official API for custom property widgets. Community implementations rely on undocumented internals.
- The SecretStorage API (Obsidian ≥ 1.11.4) stores shared secrets outside `data.json`. A report from January 2026 showed that the desktop held secrets unencrypted in Local Storage. The current status requires verification (Appendix A).
- Libraries: Davenport uses `ical.js` for iCalendar parsing and serialization (RRULE, VTIMEZONE, escaping, line folding). Davenport uses `tsdav` for the CalDAV client, and injects `requestUrl` as its fetch. Davenport uses `chrono-node` for natural-language date parsing. `ical.js` ships no timezone database. When Davenport emits `TZID` with `VTIMEZONE` (§3.1), it reuses an inbound `VTIMEZONE` definition where the zone arrived with server data. In all other conditions the synthesiser writes the definition from the bundled tzdata set (§3.2). The synthesiser is the single origin of a definition that Davenport writes. The `TimezoneService` registry of `ical.js` holds process state, and no byte of a record passes through that registry. Davenport registers a definition into it only where the library must compute a time. Davenport must be able to originate an event in an arbitrary IANA zone, even when it never received that zone before.

## 3. Data model

### 3.1 Frontmatter schema

Frontmatter carries identity and user-declared intent. All keys are top-level (flat). Rationale: Obsidian's Properties UI cannot edit nested mappings. Also, Bases and Dataview can query flat keys.

These are the keys. Each key is optional, except where this list states otherwise.

- `uid` — event identity. Davenport mints the UID when it receives the `ready` signal, or at adoption. A UID that Davenport mints at the `ready` signal therefore travels with the note before the server resource exists. Templates never mint a UID. Davenport never regenerates a UID. Any note that links to a remote event must carry `uid`.
- `state` — lifecycle intent: `draft` or `ready` (§6). A note is live (synced) when a *live* record resolves for the identity of the note. A *live* record is a record that exists, that is not tombstoned, and that is not quarantined. Liveness is not a frontmatter value. A note whose record is tombstoned is **orphaned**. A note whose record is quarantined is **suspended** (Appendix B.1).
- `calendar` — friendly calendar name. The registry resolves this name (§4.1). A push requires this key.
- `summary` — event title. When the key is absent, the value defaults to the filename. Davenport evaluates this default one time at push-creation, and never derives it again. Without this rule, a rename of a live note silently becomes a push. Materialization always writes an explicit `summary` (§8.1).
- `start`, `end` — ISO 8601. Davenport accepts `duration` (for example `30m`, `1h30m`) in place of `end`. `duration` stands in place of `end`; it does not stand alongside `end`. When a note carries both keys, validation fails and names both keys (§6.2).
- `date`, `endDate` — all-day events. `date` and `start` are mutually exclusive shapes. A note that carries both keys fails validation, and the failure names both keys (§6.2); Davenport does not resolve the conflict by fiat. Plugin writes are also shape-exclusive. When an inbound change switches an event between timed and all-day, the same write removes the keys of the departing shape. `endDate` is optional and inclusive. The serializer converts `endDate` to the exclusive `DTEND` of iCalendar. Rationale: the exclusive all-day end is the standard off-by-one-day bug, and users think inclusively. Davenport uses a single representation, and not an `allDay` boolean, because a boolean alongside timed keys permits self-contradictory notes.
- `timezone` — IANA name. Davenport resolves the zone of a time in this order: an explicit offset or `Z` in the value, then the `timezone` key, then the configured default timezone of the calendar. Serialization emits `TZID` with `VTIMEZONE`. Davenport never normalizes times to local time silently.
- `rrule` — RFC 5545 RRULE string. One note or record represents the series (§11).
- `type` — `event` (default), `task`, or `block` (§10). A block carries `task:`, which is a wikilink to the task note that the block serves.
- `due`, `completed`, `priority` — task fields (§10).
- `rsvp` — `accepted`, `declined`, or `tentative` (§12).
- `description` — Davenport pushes this key as `DESCRIPTION` (§9).
- `attachments` — a list of vault wikilinks or external URLs. Davenport pushes this list as `ATTACH` (§9).
- `alarm` — reminder offset, for example `-15m`. The serializer writes this key as `VALARM` (§13).
- `location`, `categories`, `class`, `transp`, `status` — direct property mappings (§13). `status` is the iCalendar event status (`tentative`/`confirmed`/`cancelled`), and it is distinct from `state`. The two must never share a key or a vocabulary.

Machine sync state (`etag`, `href`, hashes, base snapshots) never appears in frontmatter. Rationale: sync state in frontmatter rewrites user files at every sync. These rewrites produce git noise, and they produce cross-device merge conflicts on notes that the user did not touch.

### 3.2 The record ledger

Every synced event and every tombstoned event has exactly one record. A record is a markdown file in a configurable, visible vault folder (default `davenport/records/`). The filename is a filename-safe digest of the pair (collection href, UID). The digest is SHA-256, and Davenport computes it through the crypto of the platform. The filename is the first 32 characters of the hexadecimal form of that digest, in lower case. That set of characters is safe on every platform that §14.8 covers, and the safety therefore follows from the alphabet and not from a repair. The record stores both parts of the pair exactly, inside the file. The identity is the pair, not the UID alone. CalDAV guarantees UID uniqueness only inside one collection. iTIP scheduling *deliberately* delivers the same UID to the collection of every attendee, so that replies and cancellations correlate. Therefore, when a user receives an invitation to one meeting on two synced accounts, that meeting is two records. The same UID in two synced collections is therefore two distinct records. Where both records carry `ATTENDEE` data that suggests an invited-copy relationship, v1 surfaces the relationship; v1 does not model it. A feed event that has no UID receives a synthesized, content-derived identity (§5.2). This identity stands in the UID position of the pair everywhere. The ledger indexes (collection, UID) → path. Notes resolve to records through `calendar:` plus `uid` (§3.4). Records are the machine's truth. Records travel with the vault under every sync method, because records are plain markdown. Records are machine-owned: Davenport may rewrite a record wholesale, and a hand-edit of a record is not a supported interface. The plain-text format exists for sync granularity, for inspection, and for queries. The plain-text format does not exist for editing. Onboarding recommends that the user adds the folder to Settings → Excluded files, to keep records out of search and out of the quick switcher.

Record frontmatter holds these items: `uid`, the collection href and the resource href, `etag`, the modeled event fields as last synced, the note/venue pointer (§7), the per-instance materialization map for series (§11), the materialization content hash (§7.3), render hashes for derived content, a typed tombstone (§5.6), a normalization version stamp, and a self-checksum (below). Every record carries the core component of the stamp. A record carries the timezone component of the stamp only when that record meets one of the conditions that this section states below. The friendly calendar name of the registry never appears in a record. The name comes from the settings, and a registry rename would otherwise rewrite every record on the calendar. Names resolve from the href at read time. Render hashes are defined over the normalized base ICS property values (`DESCRIPTION`, `ATTACH`), which are server state. Render hashes are not defined over push-time rendered markdown, which only the pushing device could know. The §5.3/§9.5 freshness comparison normalizes and escapes the fresh render before it compares. No per-device fact ever appears in a record. Per-device facts include timestamps, cursors, and device IDs. These facts are device-local (§3.3), because per-device content inside a shared file makes divergence structural. The record body holds the last-synced ICS in a fenced code block, normalized through `ical.js` canonical serialization. That body holds no `VTIMEZONE` for a zone name that the bundled table holds; the paragraphs on the timezone component below state that rule. This ICS is the base snapshot for three-way comparison (§5.4) and the substrate for round-trip patching (§5.5). Normalization exists so that two devices that hold the same server state hold byte-identical records. Providers may re-serialize at each fetch (Appendix A item 16).

Records are byte-deterministic pure functions of (server state, venue pointer, materialization map and content hash, tombstone). Davenport writes a record only when the computed content differs from the file (write-if-changed). The normalization version stamp indexes the determinism, and the stamp has two components. The core component covers three inputs to the byte form. The first input is the set of rules that fix the order and the folding of the canonical ICS text. The second input is the serializer of `ical.js`. The third input is the emitter that writes the frontmatter of the record. Davenport owns that emitter, and Davenport uses no YAML library to write a record. The emitter takes the closed schema of a record, and golden byte-exact fixtures pin every byte that it writes. No version of a library can therefore move the frontmatter of a record, and this answers Appendix A item 19 for the frontmatter half of the byte form. Every record carries the core component.

Davenport uses two timezone datasets, and this spec keeps the two apart. The bundled table is the timezone dataset that the plugin ships. §2.2 names this dataset the bundled tzdata set. An owned generator pins one IANA release and writes the table into the source of the plugin. The host database is the timezone dataset that the operating system of the device supplies. Every device that runs one plugin build holds the same bundled table, and the host database differs from device to device.

The timezone component covers two inputs to the byte form: the release of the bundled table, and the synthesiser. The synthesiser is the code that writes a timezone definition from the bundled table. The timezone component indexes every byte of a record that the bundled table can reach, and it states which release and which synthesiser interpret a zone name that the record carries.

A record carries no timezone definition for a zone name that the bundled table holds and that a value of the event references. A reference stands in the timezone parameter of a value, and a reference also stands in the value of a property: a calendar states its home zone in a value that way. The record carries the name, and it carries the timezone component. A device that needs the definition of such a name computes that definition from the bundled table with the synthesiser. The computation is deterministic: the bytes follow from the name and the table alone. No device stores, syncs, or compresses a definition for this. A definition that the server sent under such a name canonicalizes. The record stores the reference. A change on the server that moves only such a definition therefore compares as a no-op, and the next push writes the canonical definition in its place. A record embeds a definition verbatim for a zone name that the bundled table does not hold, because no device can compute that definition. A record also embeds a definition verbatim where no value of the event references that zone. Davenport does not model the reason that such a definition stands in the calendar, a push writes back only what the record holds, and no reference would bring the definition back. A record carries no content hash for a zone: the self-checksum and the golden gate carry the integrity duty. The duty of the record writer therefore has three parts. The writer carries the name and the stamp for a name that the table holds and a value of the event references. The writer carries the definition of the server in every other case. Every definition that leaves a record stands under a name that the record still states, so a push writes back every definition that a record dropped. Every record file uses the line feed alone as its line ending, in the frontmatter and in the fenced block, and a tool that converts a record file to another line ending breaks the self-checksum of that record.

The measured reason for the reference: a New York definition costs about 8.4 kB in each record, and a calendar of 2,000 events repeats those bytes into about 17 MB of vault text. A reference costs tens of bytes. This spec accepts the consequence: a record alone no longer holds the rule history of its zones, and a regeneration of that history needs the plugin or a copy of the IANA database. The wire stays separate from the record. A push writes a complete definition into the uploaded object, because the format requires one.

Three reaches are known, and each one is visible in the record itself. A record carries the timezone component under any of these three conditions. First, the record names a zone. A record names a zone where a value of the record stands in that zone, where the record carries the definition of a zone, or where a value of the record states the name of a zone that the bundled table holds. The table decides which of the two forms above a record holds for a name, and both forms are bytes of the record, so this condition asks for the name alone and asks nothing about the table. Second, the record carries a repeating series whose end stands in universal time, under a time that names a timezone and that governs the series. The time that governs the series is the start of the component, or the due date where the component states no start. That time states a date and a time of day, and so does the end of the series. The format states such a series end in universal time, so an edit of that end converts a local time through the bundled table. A series that states its end as a date reaches no such conversion, and a series whose governing time states a date reaches none either. The second condition reads this shape of the record, and it does not read the origin of the value. Third, the record carries an instance date that Davenport computed in the zone of the event (§11). A record that meets none of the three conditions carries no timezone component. This list holds the known reaches, and the list is not closed. A change that gives the bundled table a new reach into the bytes of a record must add the condition of that reach to this list, in the same change.

Each component is one monotone integer: a component never decreases from one plugin version to the next. The byte form depends on the version of `ical.js` in use, and on the version of the owned emitter (Appendix A item 19). Multi-device vaults also routinely run mismatched plugin versions. Each device holds its own value for each component. The skew rule therefore compares each component on its own, and it compares only the components that the record carries. A device rewrites the record one time and wins when both conditions hold together, and only then. First, no compared component of the device is older than the same component of the record. Second, at least one compared component of the device is newer. In every other condition the device treats byte-only differences as a no-op and suppresses its rewrite. For example, a device that is older on the core component and newer on the timezone component suppresses, because one of its compared components is older. Without this rule, version skew produces permanent rewrite ping-pong. The comparison that stands in front of this rule passes over a timezone definition that one record carries and the other record does not, under a name that a value of the event references. The bundled table decides whether such a definition stands in a record, so that difference states a release of the table and not a change of the state. The comparison reads a definition that both records carry, because a device keeps such a definition only where its table lacks the name, and a difference in those bytes therefore comes from the server. Without this treatment of the base snapshot, two devices at two releases of the table reach the skew rule for no record, and they rewrite in turn.

Rationale for determinism: every device applies every inbound change, so record files are the most concurrently-written files in the vault. Determinism plus write-if-changed makes convergent devices produce zero writes and zero sync conflicts. Two devices can hold different server versions, where one version is stale. In this condition, convergence arrives through two channels that cooperate. Do not "fix" this behavior. First, the fetch of the stale device fast-forwards its record to identical bytes, and writes nothing. Second, the note copy of the other device arrives through vault sync and corrects the linked note. The inbound engine of the stale device does not correct that note: its comparison against the fast-forwarded base correctly sees no remote change.

These checks read a file of the standing records folder, where a file that fails to parse is a damaged record; §15.2 states the other context, in which a file that fails to parse is a user file of a folder that a settings change proposes. Three operational checks trigger quarantine, and Davenport can build all three from machinery that this section already requires. If any one of these conditions is true, Davenport quarantines the record. (a) The file fails to parse, or the file fails schema validation. (b) The filename does not equal the digest of the identity that the file contains. The naming convention is an integrity invariant, and conflict copies and hand-copies break it by construction (per-tool conflict-copy filename patterns: Appendix A item 20). (c1) The self-checksum fails. Every record write stores a hash of the canonical bytes of the file, with the checksum field blanked. The hash is SHA-256, and the field holds all 64 characters of the hexadecimal form. Verification therefore needs no ability to recompute the canonical form, and it runs on every device at every version. Merge mangles break the checksum with overwhelming probability. This closes the window in which a device that is older than the record on a stamp component would otherwise admit a mangled record into its three-way base. (c2) A recompute of the canonical record from the file's own parsed inputs does not reproduce its bytes. This check applies only where each compared stamp component of the device equals the same component of the record. Recompute-mismatch is the semantic check. Recompute-mismatch is also the operational definition of a merge mangle that the checksum somehow survived. Davenport surfaces quarantined records and excludes them from every consumer, and it offers a rebuild path. Rebuild is asymmetric, and the spec says so: `etag`, the hrefs, and the base ICS re-fetch from the server. The venue pointer and the materialization map exist only in the record. Their loss falls back to routing and adoption suggestions, and this fallback is lossy. Rebuild has two branches with opposite dirty dispositions, so neither branch may fall through the wording of the other. In the first branch, the re-fetch succeeds → the record is live. In this first branch, the dirty entries that accumulated while the note was suspended evaluate normally (B.1). In the second branch, the re-fetch answers `404` → the rebuilt record is a remote-observed tombstone. In this second branch, the suspended note becomes orphaned, and the accumulated dirty entries go inert, per the orphaned rule of B.1. A `404` is routine, because Davenport excludes inbound processing for a quarantined identity while the sync token advances past a deletion. There is one exception to quarantine noise. When a conflict-copy record differs from its sibling only in tombstone type, it auto-resolves by type dominance (§5.6), and Davenport does not surface it. The event is already gone.

Rationale for per-event markdown files instead of `data.json`: `data.json` is a single blob. Concurrent offline changes on two devices therefore resolve as whole-file conflicts, and they silently drop intent (for example, the tombstone of one device). Per-event files give sync tools per-event merge granularity. Davenport uses markdown, and not `.json` sidecars, `.ics` sidecars, or a hidden folder, because only markdown syncs unconditionally (§2.2). Dataview can query records that carry frontmatter. Note that Obsidian's Excluded Files setting currently also hides files from Bases. Exclusion from search and Bases queryability therefore trade off; they do not coexist (Appendix A item 18). The exclusion recommendation stands, and this spec documents ledger queries as a Dataview capability until that condition changes.

### 3.3 Device-local state

Davenport stores these items through `saveLocalStorage`, or through IndexedDB for bulk: the sync-tokens and the CTags for each calendar, the device ID, the UI state, regenerable caches, and the dirty set (§5.3). Rationale: from the view of the server, each device is a distinct sync client. Cursors that travel between devices corrupt incremental sync. Each device-local item must satisfy one of two conditions. It is regenerable from the server plus the ledger, or its loss degrades to a surfaced question and not to a wrong write. The dirty set satisfies the second condition.

### 3.4 Identity rules

- Davenport mints UIDs. Templates must not contain `uid` keys. Validation rejects template-supplied UIDs.
- Notes resolve to records through `calendar:` plus `uid`. Notes never resolve through `uid` alone, because one UID legitimately exists in more than one collection (§3.2). Materialization and adoption therefore always write `calendar:` (§6.3, §8.1).
- Davenport always detects two *notes* that claim one (calendar, uid) identity, because the ledger indexes identity → path. Recovery treats the newer file as a copy: it strips `uid`, it keeps the event fields, and it sets `state: draft`. Rationale: the dominant cause is the duplication of last week's meeting note to prepare this week's meeting note. Without recovery, the sync loop moves last week's meeting. Duplicate *record* files are a different failure with a different handler, the quarantine of §3.2. This rule never applies to records.
- File renames do not affect identity. Davenport watches vault rename events and updates the pointer of the record.
- A `uid` that is present with no matching record is an inert state: Davenport never pushes it, never re-creates it, and never offers it for adoption. The converse binding is also never automatic. A record that Davenport newly mints from a server-observed resource does not auto-bind to an existing note that carries the same identity. Davenport surfaces the pairing as an adoption suggestion. Rationale: UID reuse by other clients is legal, and an auto-bind trusts an identity that the vault did not mint and did not verify. This inert state is routine during vault-sync flight, because a note file can arrive before its record file. Davenport surfaces the state in Needs Attention only when the state persists past the grace period (§5.3). A persistent item names its resolutions. One resolution is to look up the identity on the server with a `calendar-query` that carries a UID property filter. A found identity yields an adoption suggestion; no-auto-bind still holds, and the user confirms. A not-found identity yields nothing to link. Another resolution is to strip the note to draft: the fields stay, and a later push mints a fresh identity. Another resolution is to strip the identity entirely. A server that does not honor the UID filter degrades legibly. The lookup action reports the filter as unavailable. The lookup action does not return a false not-found (Appendix A item 25). Creation itself is race-safe, independent of this rule. Creation `PUT`s use `If-None-Match: *` (§5.5). Therefore two devices that race to create one UID converge, and they do not produce a duplicate.

## 4. Accounts, calendars, secrets

### 4.1 Registry

Settings define the accounts. Each account has a server URL, a username, and a credential reference. Davenport discovers the calendars and the task lists of each account. To discover them, Davenport walks the collections with `PROPFIND` and reads `supported-calendar-component-set` for each collection. Davenport gives a friendly name to each calendar and to each task list. A registry entry holds the friendly name, the account, the collection href, and the ownership mode. The entry also holds the accepted component types, the default timezone, the default templates, and the per-calendar options that this spec refers to throughout. The registry resolves the `calendar:` values in frontmatter. If the registry cannot resolve a name, validation fails legibly.

### 4.2 Ownership modes

Every calendar has exactly one mode. Registration sets the mode, and the mode can change later. The modes are:

- Vault-owned — the vault is authoritative. Local changes push. A per-calendar setting decides what happens to remote changes: Davenport either surfaces them as conflicts or overwrites them. Auto-push-on-valid skips the `ready` gate. It is an opt-in, and it is available on vault-owned calendars only. This opt-in is the one sanctioned exception to principle 3. The opt-in earns its rationale like every other exception. First, the opt-in is itself a standing signal. Second, the opt-in has a scope of one calendar with a single writer. Third, the attendee gate still applies to each write.
- Remote-owned — a read-only mirror. Push transitions are not available, and the UI says so. If a note targets a remote-owned calendar and carries `state: ready`, Davenport produces a visible warning and does not stay silent. A note with `state: draft` produces no warning, because drafts are local-only planning and are legitimate on any calendar. A field edit on a live note that links to a remote-owned record is divergence, not intent. *Dirty* divergence (§5.3) surfaces immediately in Needs Attention with revert and copy-out actions. The next inbound change overwrites that dirty divergence, and the attention item preserves the overwritten values. Preservation items resolve by acknowledgment and never by self-dismissal (§14.3), because the displacement is historical and has nothing to resolve to. Not-dirty divergence follows the inert path and the grace path of §5.3 without change. Vault-sync flight skew on mirrored calendars therefore never prompts. The "push" action of the §5.3 grace prompt does not exist here. The §4.2 item preempts that action. ICS feed calendars are always remote-owned.
- Bidirectional — Davenport does full reconciliation per §5.

The default mode for a newly added CalDAV calendar is remote-owned. Rationale: the danger analysis in §6 analyzes shared calendars. The safe default is the mode that cannot write.

### 4.3 Secrets

An account uses one of two credential types: an app-password (HTTP Basic) or an OAuth token source (Bearer; §4.4). Davenport stores credentials in Obsidian SecretStorage when SecretStorage is available (≥ 1.11.4). On older versions Davenport falls back to `data.json`, and it shows a persistent warning on the settings screen. Credentials never appear in frontmatter, in records, in logs, or in exported files. The README must not claim encryption at rest until Appendix A item 1 is verified. Onboarding recommends app-passwords whichever storage Davenport uses, because an app-password limits the blast radius.

### 4.4 OAuth accounts (Google)

A Google account authenticates with OAuth 2.0 against the CalDAV v2 endpoint. The engine does not change. The OAuth support of `tsdav` handles Bearer authentication and token refresh.

- Flow: Authorization Code with PKCE and a loopback redirect. Davenport runs a transient local HTTP listener (Node API; desktop only). Davenport then opens the system browser at the consent page. Davenport then exchanges the returned code. Davenport stores the refresh token per §4.3. A mobile device cannot run the listener, so authorization happens on the desktop. The cross-device behavior of SecretStorage decides whether the stored token reaches mobile (Appendix A item 7).
- v1 posture — bring-your-own credentials: the user creates a Google Cloud project and a Desktop OAuth client. The user then enters their own client ID and secret. Rationale: this posture has no verification process and no user cap, and it embeds no client secret in an open-source repository. The setup guide must instruct users to publish their OAuth app to production (unverified) status. An app that stays in Testing status expires its refresh tokens after seven days. The user must then authorize again every week.
- v2 stretch goal — shared client ID: ship one client ID, so that users skip the Cloud Console entirely. This goal requires Google's verification for the sensitive Calendar scope (privacy policy, brand verification, periodic re-review; Appendix A item 9). This goal is not a v1 commitment.
- Limitations: Google over CalDAV carries events only. It has no VTODO (Google Tasks stays out of scope, §17) and no managed attachments. RFC 6578 support and iTIP behavior on attendee writes require verification (Appendix A items 8 and 10). Until that verification, Davenport assumes that the attendee gate (§5.5) is maximally live on Google calendars.

## 5. Sync engine

### 5.1 Loop

For each calendar, Davenport does these steps on a configurable interval and on a manual command:

1. Incremental: send a `sync-collection` REPORT with the stored sync-token. Use the fallback where the server does not support RFC 6578, or where the server rejects the token. In the fallback, compare the CTag. If the CTag changed, send a `calendar-query` over the sync horizon and diff the result against the records. Diff only the records whose events intersect the horizon window. The fallback does not touch out-of-horizon records. Without that scoping, every token rejection would misread all historical records as remote deletions. Absence from the fallback results never mints a tombstone directly. A `calendar-query` reports what intersects the window, not what exists. Also, an event can be rescheduled across the horizon boundary after the last good sync. The record of that event still intersects the window, but its server resource does not. The absent set is normally small: it holds the true deletions plus the boundary-crossers. Confirm the absent set at href level with one batched `calendar-multiget` (records store resource hrefs). A `404` confirms the deletion and mints the remote-observed tombstone. A `200` reveals the move and updates the record. That record then follows the out-of-horizon staleness acceptance (§5.7). Rationale: remote-observed tombstones drive banners, orphaning, and the eventual pruning of exactly the fields that a rebuild cannot recover. An inference must not be load-bearing when one cheap batched request can replace it with an observation.
2. For changed hrefs: send a `calendar-multiget`. Locate the records by (this collection, UID). The resource href locates the same records, and records store that href. Then apply the inbound changes (§5.4). A reported href with no record mints a record, in the horizon or out of it, per the membership policy of §5.7.
3. For local pending changes (§5.3): validate them, serialize them, then push them (§5.5).
4. Process tombstones (§5.6).

A failed request retries with exponential backoff. Davenport serializes the writes to one server. Davenport batches the reads with multiget. Rationale: self-hosted servers are routinely slow or unreliable. Too many requests change that unreliability into data races.

### 5.2 Feeds

Davenport re-fetches each whole ICS subscription feed on the same interval. Davenport diffs the feed against the records by (collection, UID). The change marker is a content hash of the normalized component, and `SEQUENCE` is the tiebreaker. Many feed generators stamp a fresh `DTSTAMP` on every fetch. As a marker, `DTSTAMP` would rewrite every feed record on every poll. Feed records are never push targets.

Three gates precede any feed diff, and the cheapest gate comes first. First, Davenport discards a whole fetch that does not parse as a complete `VCALENDAR`. It runs no diff and writes one logged line. This gate disposes of truncated responses and login-wall HTML before they can masquerade as mass deletion. Second, Davenport clips enumeration to the horizon, but it does not clip existence. Davenport mints and updates records only for events that intersect the horizon (§5.7). A decade-spanning holiday feed does not deserve a decade of records. Davenport computes the *vanished* set against the unclipped fetched file. The reason is that an event outside the window but present in the file is out-of-horizon, not deleted. This gate is the feed analogue of the confirmation rule of §5.1. In a feed there is no href to confirm, and the whole file is the confirmation. Third, mass vanishing is anomalous before it is deletion. When more than a threshold share of the records of one feed vanish in one poll, Davenport holds the tombstones for the vanished set. Davenport then surfaces one feed-level anomaly instead of per-event banners. The threshold default is one quarter of the records and at least five records, and the user can configure both values. Davenport then content-pairs the vanished set and the appeared set. If Davenport finds pairs, the generator mints fresh UIDs on each fetch, and the anomaly offers a sticky per-feed switch to content-derived identity. If Davenport finds no pairs, the cause is truncation or an outage upstream. A following poll that restores the events then clears the hold silently. Held tombstones apply only when the user explicitly accepts them. To accept the identity switch is a bulk re-key, not a bulk deletion. The records of the feed migrate to content-derived identity in the accepting poll. The content pairing that diagnosed the instability supplies the old-to-new mapping. The venue pointers and the materialization entries transfer along that mapping. Davenport shows no per-event banners, and it writes no tombstones for the re-keyed set. Events that the pairing could not match fall out as an ordinary vanish-plus-appear under the new identity. That result is the stated cost of content keying, and the feed incurs it once. Rationale: feeds are stage 1, the release whose entire job is to demonstrate trust on the read path. A misbehaving generator must produce one legible question, not a banner storm.

An event genuinely vanishes from a re-fetched feed when three conditions hold together. First, the fetch parsed complete. Second, the event is absent from the unclipped file. Third, the vanishing stays below the mass-vanish threshold. Such an event produces a remote-observed tombstone. `DELETE` is unreachable for feeds in every case, and the typing drives the banner.

Feed identity tolerates what feed generators actually emit, not what RFC 5545 requires of them. A UID that is present and unique within the feed is the identity, per §3.2. An event that lacks a UID receives a synthesized identity. That identity is a content-derived hash of the normalized component, and it stands in the UID position of the (collection, UID) pair. This spec states the limitation plainly: a content-keyed event has no identity across edits. An edit is therefore a vanish-plus-appear, and continuity does not survive it. Continuity here means the venue pointer and the materialization. The same content hash disambiguates duplicate UIDs within one feed. Duplicate UIDs also raise the feed-level anomaly, because they are the same species of generator misbehavior. Rationale: real generators omit UIDs, duplicate UIDs, and re-mint UIDs on each fetch (Appendix A item 23). The identity keystone must not shatter on the first thing that users touch.

### 5.3 Local change detection

Davenport watches the `metadataCache` change events on notes that bear a `uid` key or a `state` key. Davenport watches the `state` key because a first push happens on a note that has no UID yet. Davenport does not treat a file inside the records folder as a note (§3.2). The path of the records folder is configuration (§15.2), and every file that Davenport writes there is a record. A record bears a `uid` and no `state`, and Appendix B defines that shape as a bound note. Every record file therefore bears a `uid` key. The exclusion names the folder and not the shape. A file that a user puts in the records folder is therefore not a note, and every note-side rule is inert for that file. The note-handling exclusion of this section follows the setting. A change of the path (§15.2) moves that exclusion to the new folder, and the same operation moves the record files. The refusals of §15.2 keep user files out of the new folder, so a path change captures no note. A file that stays behind in the old folder leaves that exclusion, and Davenport reads such a file as an ordinary file of the vault again. Davenport pushes event-relevant frontmatter changes after a debounce. The debounce waits for editor idle plus a few seconds, and Davenport batches the changes. Davenport also checks the derived content, which is the description and the attachments. To check it, Davenport compares a fresh render hash against the stored hash of the record at sync time. This check is necessary because embeds make the inputs span multiple files (§9.5).

The release rule above has one exception, and the exception is a record. A file that is a record of Davenport stays outside note handling in every folder. The file is a record when the file parses as a record under the schema of §3.2, and §15.2 states that test. A file that Davenport holds in quarantine as a record is also a record. Both rules read the file and not the folder, so the answer does not change with the place of the file. The folder exclusion above names the folder and not the shape. This exception names the file and not the folder. The two together hold every file of the records folder outside note handling, and they hold every record outside note handling. Davenport therefore reads no record as a note, and no note-side rule writes to a record. The duplicate-identity recovery of §3.4 never applies to a record, and §3.4 states that limit. Davenport meets a record that stands outside the records folder through this section, because a record bears a `uid`. Davenport then surfaces that file as a record that stands in the wrong folder, and the surface names the identity of the file and the path of the file. Three events put a record in that place, and §15.2 states the first two: a move-back that fails, a crash during a move, and a device that did not receive a new path and therefore still writes records at the old path (§15.2, §5.1). The user resolves the surface. The user moves the file into the folder that the setting names, or the user removes the file. Davenport never resolves the surface with a write to the file.

Divergence alone is never intent. Davenport derives the pending set: the set holds every live note whose declared fields differ from the base snapshot of its record. Davenport *pushes* a divergence only when both conditions hold together. First, the note is in the device-local dirty set. Second, the mode of the calendar permits a push (§4.2 governs remote-owned calendars). The device-local dirty set holds the paths whose modification events this device itself observed. The writes that Davenport performs itself never enter the dirty set. These writes are the inbound application, the adoption backfill, and the `state`-key removal. Obsidian tags no write origins, so Davenport recognizes its own writes by expected-content matching. In expected-content matching, the watcher compares the changed file against the content that Davenport just wrote. The misattributions of this match are benign in both directions. If the match swallows a user edit, the edit degrades to the surfaced path. If the match mistakes a self-write for the user, Davenport yields a dirty entry over a divergence. That divergence lasts only until the base snapshot write lands, because the apply order writes the note first. The entry clears with the divergence under the clear-on-no-divergence rule below. Where a crash interrupts that pair of writes, the surviving entry pushes, meets `If-Match`, and converges. That behavior is the backstop of §5.4. Davenport generation-stamps the dirty entries with a per-path sequence or with the content hash that it captures at push start. Clear-on-success removes an entry only if no modification event postdates the push snapshot. An edit made during push flight therefore stays dirty and pushes on the next loop. It does not degrade to a delayed prompt. Entries also clear when the divergence disappears.

Davenport holds a divergence without a local dirty entry inert, and presumes vault-sync flight. The record and the note arrive as separate files in no guaranteed order. A record can arrive before its note. To treat that skew as an edit would push stale values and silently revert edits made on another device. An unexplained divergence can persist past a grace period after the last vault write to either file. Davenport then surfaces the divergence in Needs Attention, and never resolves it automatically. The grace period default is 10 minutes, and the user configures it in Sync settings. The surfaced item must show the divergent values for each field, because the user cannot otherwise know which side is stale. The surfaced item must default to inspect and not to push. The surfaced item self-dismisses when the divergence resolves (§14.3). Its designed resolution is a late-arriving file, not a click. Derived-content divergence is exempt from grace surfacing entirely. The documented snapshot semantics of §9.5 *explain* a fresh render that differs from the stored hash. The fresh-render comparison has only one job: it decides whether the description and the attachments participate when a push already happens. A push already happens for dirty declared fields, or for the explicit refresh command. Orphaned notes and suspended notes are likewise exempt from grace surfacing. The banner is the surface for these notes. A second prompt whose push action is wrong in both states would be noise (Appendix B.1). Davenport cannot distinguish edits made outside Obsidian while Obsidian is closed from a sync arrival. These edits therefore take the surfaced path by design, and they do not push automatically. The loss of the dirty set (device-local, §3.3) therefore degrades to a question, not to a wrong write. A same-field remote change can erase the divergence before the grace prompt fires. In that case the not-dirty preservation of §5.4 carries the displaced value, so the question survives the overwrite.

### 5.4 Inbound changes and conflicts

Inbound application is a field-level three-way comparison. It compares the local declared fields against the base snapshot of the record, and the remote event against the same base. It has one gate that it inherits from §5.3: the "local changed" leg requires the note to be *dirty*. Davenport presumes that a not-dirty divergence is flight, and it takes the inbound apply. Without this gate, flight skew plus a concurrent remote change raises a conflict. That conflict offers a stale value that nobody intends, and it leaves the actual last edit of the user off the ballot. (A real offline edit whose dirty entry was lost thereby loses conflict detection. It lands in the surfaced-question path of §5.3, which is the designed loss mode.)

- Remote changed, local unchanged (the note's value equals the base): apply the remotely changed fields to the record. Where a note is linked (per the mutual-claim rule of §7.1), also apply those fields to the frontmatter of that note with `processFrontMatter`. Then update the base snapshot. Vault-sync flight lands here by construction, because a stale note copy carries the previous base value. Flight skew therefore stays silent.
- Remote changed, local changed but not dirty (three distinct values on a not-dirty note): apply the remote value exactly as in the case above. The rationale of the dirty gate stands, and flight-adjacent states must never raise conflicts. Also preserve the displaced note value in an acknowledgeable attention item with revert and copy-out actions. This item mirrors the remote-owned handling of §4.2. Rationale: this is the one path where a same-field remote change meets an edit that the engine cannot attribute. The engine cannot attribute an edit made outside Obsidian while Obsidian was closed, or an edit whose dirty entry was lost. Without preservation the overwrite is silent, which is the counterexample to the degrades-to-a-question guarantee of §5.3. The three-way comparison already computes the discriminator. The rule adds no machinery. It adds only a surface.
- Local changed (dirty), remote unchanged: take no inbound action. The local change pushes per §5.5.
- Both changed, different fields: merge silently. Apply the remote fields. Keep the local fields. Push the local fields. Rationale: "remote moved the meeting, I edited my description" is the common case, and to surface it trains users to ignore conflict prompts.
- Both changed, same field, same value: this state is convergence, not conflict. Inbound application is a no-op whenever the remote value equals the base value, or the remote value equals the local value. Rationale: the edit of one user routinely arrives at a device twice, once by CalDAV and once by vault sync. To raise a modal for it is the prompt-fatigue failure that this section exists to avoid. A same-field conflict requires three distinct values.
- Both changed (dirty), same field, different values: this state is a conflict. Surface it with a modal or with a note-level marker that shows both values. Never resolve it by last-writer-wins. The choice of the user updates the frontmatter and the record. If the local side wins, the choice also pushes.

Application writes in a mandated order: the linked note first, then the record and its base snapshot. The base snapshot may lag the note that it summarizes. The base snapshot must never lead that note. A crash after the note write leaves local equal to remote over a stale base. The next loop resolves that state as silent convergence, because remote-equals-local is a no-op in the list above. The reverse order fabricates a divergence that the user never made. A note that trails a prematurely advanced base reads as changed-but-not-dirty against an "unchanged" remote. That fabricated divergence self-heals only where the symmetric apply of another device delivers the missing note write. On a single-device vault it degrades to a §5.3 grace question. If the interrupted self-write escapes expected-content matching and enters the dirty set, the resulting push meets `If-Match` on the advanced etag of the server. The push then converges. That convergence is a backstop, not a design. This spec states the order for the reason given in §10.4. Where a crash can land between two writes, which write goes first is a design decision, not an implementation accident.

Every device applies every inbound change to the same linked note, so per-note write determinism is load-bearing. Convergence requires `processFrontMatter` to emit identical bytes for identical inputs across devices (Appendix A item 11, a design input). If the verification fails, a designated-writer rule is required before stage 2. Concurrent edits to the same note on two devices resolve at the sync-tool layer, outside the plugin. The output of the tool can re-enter §5.3 as dirty. The `If-Match` path plus the attendee gate are the named backstops, because the engine does not see every divergence first.

A binding invariant governs the bytes of a record. The bytes of a record are a pure function of three inputs: the bytes that the server sent, the intent that the vault holds, and the value of each stamp component that the record carries. Vault intent is the venue pointer, the materialization map with its content hash, and the tombstone (§3.2). An offset that the host database supplies never reaches those bytes. §3.2 defines the host database and the bundled table. A result that Davenport computes from the bundled table may reach those bytes, and the timezone component of the stamp indexes every such result. Rationale: two devices can hold different host databases, and the two can then compute different offsets for one wall time. A record that depended on a host-database offset would differ between those devices, and the ledger would never converge.

A per-calendar setting with two values governs the remote deletion of an event that has a linked note. **Flag** (the default): write the remote-observed tombstone (§5.6) and banner the note. The file survives. **Remove**: also move the note to trash. Use the trash API of Obsidian, honor the deleted-files preference of the user, and never delete permanently. Move the note to trash only when both conditions hold together. First, Davenport created the note. Second, the content of the note still matches the materialization-time content hash that the record stored at creation (§7.3). A note that the user has touched degrades to flag, and so does a note that Davenport did not create. Davenport logs the reason. The option exists to clean up hollow mirror notes, and it must never delete words that a user wrote. Davenport writes the tombstone before the trash operation, for the reason given in §10.4. The crash-reachable intermediate state (tombstone present, note still present) is an ordinary orphaned note. The reverse order would leave a live record with a dangling pointer that masquerades as a user deletion. A trash operation under this setting carries acknowledgment semantics (§5.6: to delete an orphaned note acknowledges it). The tombstone therefore becomes claimant-free and prunable after retention. Another device can receive the trashed note before the tombstone record. That device surfaces a transient dangling-pointer item, which self-dismisses when the tombstone arrives (§14.3). The setting governs the linked note file only. Materialized venue sections always stay (§7.5).

### 5.5 Push semantics

Every `PUT` sends `If-Match` with the etag of the record. A creation `PUT` sends `If-None-Match: *` instead. A creation `PUT` targets `{uid}.ics` within the collection, because servers can be strict about the agreement between the basename and the UID. A `412` on creation means that another device already created this UID. In that case, fetch the resource and converge. Do not raise an error. A `412` on update is a conflict signal. Pull the resource, run §5.4, and retry only after the resolution. Every successful write bumps `SEQUENCE`. It also updates the etag, the base snapshot, and the hashes of the record. The precondition machinery is a named backstop (§5.4, §6.1, Appendix B row 25) only where the server enforces preconditions. The enforcement is verified for each provider, not assumed (Appendix A item 24). The pre-stated branch for a server that does not enforce preconditions is per-provider documentation plus a per-account trust caveat in §14.4. No mechanism substitutes for a precondition that the server ignores. The job of the caveat is therefore to keep the limitation legible instead of discovered.

Round-trip rule: a push is a patch that Davenport applies to the base ICS of the record. A push is never a regeneration from the frontmatter schema. Every property that Davenport does not model survives the round trip. These properties include vendor `X-` properties, VALARMs that Davenport did not create, and structured locations. The survival is semantic, and it is not a promise of identical bytes. Only the path that parses the ICS text and serializes it again can write such a property in a different form. That form keeps the same meaning. There is one known change of meaning, and this spec accepts it: a vendor parameter that carries more than one value collapses to one value that holds the commas. No part of Davenport removes an unmodeled property. Rationale: a regeneration silently strips the data of other clients on every write. Users experience this as "Davenport deleted my alarms."

Attendee gate: a `PUT` or a `DELETE` can target a resource that has `ATTENDEE` properties, that would gain them, or that would lose them. Every such request requires a confirmation for each write, in every mode, with no opt-out. The gate is a predicate, not a list. Enumerations of the gated verbs were found incomplete twice. These cases are illustrative. The gate applies when a write creates an event with attendees. It applies when a write adds an attendee. It applies when a write removes an attendee (the removed party receives `CANCEL`). It applies when a write changes the time, where "time" includes `rrule`, `duration`, and `timezone`. It applies when a write deletes an attendee-bearing event (iTIP `CANCEL` to all). It applies to any other organizer modification that servers may propagate as updates, including the summary, the location, and the description. The gate includes the §9.5 refresh command. Err toward over-gating. Rationale: scheduling-capable servers email attendees on write, and nobody can unsend an email.

### 5.6 Deletion and tombstones

Tombstones have a type that comes from their origin. A local-intent tombstone records a retraction or a deletion that a user decided on some device. A remote-observed tombstone records that the server no longer has the resource. Only local-intent tombstones issue a `DELETE`, and that `DELETE` carries `If-Match`. Remote-observed tombstones never write to the server. A `DELETE` answered by `404` is a success, because another device got there first. A `DELETE` answered by `412` means that the resource changed after the deletion was decided. Surface that answer with two choices: delete anyway, or keep. Never force the deletion with a refetched etag. `Keep` clears the tombstone. The record revives to live, re-fetches the changed resource, and re-enters §5.4. Davenport retains the pointer where a note still claims the identity. Otherwise the revived record lands venue-less in routing/inbox. For the keep-both case of §10.4 this result is exactly right. The reason is that the note belongs to the successor identity, and the inbox holds the old event for re-homing. Tombstone type is monotone: remote-observed may upgrade to local-intent, and never the reverse. The typing is a genuine two-writer race on one record file: one device tombstones local-intent while another device observes the server deletion first. Every device therefore re-canonicalizes to the strongest type that it has seen, on its next loop. That re-canonicalization makes one rewrite, and the type is then stable. The strongest-seen memory is device-local (§3.3). The loss of that memory degrades to a best-effort banner correction. That degradation is acceptable, because the stakes are label-only in every reachable race: the `DELETE` already succeeded, and nothing resurrects. A conflict-copy record that differs from its sibling only in type auto-resolves by dominance (§3.2). Tombstoned records retain the tombstone for a retention window before pruning. Davenport never prunes a tombstone whose identity a note still claims, until the user acknowledges the banner of that note. The acknowledgment strips the `uid` key and the `state` key from the note, and returns the note to a plain note with its fields intact. To prune under an unacknowledged claim would let a later same-UID resource bind silently to a stranger. The resource of a remote-observed tombstone can reappear server-side within the window. The record then revives to live. An unacknowledged orphaned note relinks, and its banner self-dismisses. The orphan-era dirty entries clear. The contract of orphaned was "the event is gone, edits are local-only," and a revival must not convert that promise into a push. A divergence after the revival therefore takes the inert path and the grace path, and it surfaces as a question. The deliberate asymmetry with suspended stands. The contract of suspended is "temporarily unreadable, will resync", and the dirty entries of a suspended note survive a rebuild. A reappearance after the acknowledgment is a revival that lands unlinked within retention, and a genuinely new record after pruning. Both cases route to inbox, and no-auto-bind holds in both. A remote-observed tombstone in one collection can pair with a same-UID resource that appears in another collection of the same account. Davenport then surfaces a *move suggestion* on the orphaned note. When the user accepts the suggestion, Davenport updates `calendar:` and transfers the venue pointer. The move is never automatic. Davenport suppresses or caveats the suggestion when both sides carry `ATTENDEE` data that suggests invited copies rather than a move. A cross-account same-UID never suggests, because it is more likely an invited copy than a move. This spec states the manual path for discoverability. First, acknowledge the banner. Then adopt. Tombstones live in the ledger. They do not live in device-local storage. Rationale: a deletion decided on one device must reach the other devices via vault sync. If the deletion does not reach them, the next pull on another device resurrects the event. The origin typing exists for this reason. Without the typing, the reader cannot determine the origin of a tombstone. Such a tombstone could escalate a misdiagnosed remote deletion into a `DELETE` against a live event.

This spec acknowledges one mislabel. A device may observe a server deletion before the local-intent tombstone record of the originating device arrives by vault sync. That device banners the note "remotely deleted". The states converge. When the local-intent tombstone arrives, Davenport corrects the banner to reflect that the deletion was the user's own.

A note file deleted while Obsidian is closed produces no vault event. Davenport then discovers a record whose note pointer dangles. A dangling pointer never auto-deletes the server event. The resolution first checks whether a different path now bears the identity, and it offers relink first. This check is necessary because a rename made while Obsidian was closed looks exactly like deletion-plus-new-file. Venue notes bear no identity, so their relink check is different by necessity. Davenport matches the records that point at the vanished path against a same-named or near-named file that appears near-simultaneously. Davenport uses the fuzzy machinery of §6.3 for this match, because some sync tools deliver renames as delete-plus-create pairs (Appendix A item 21). Davenport clears the materialization-map entries for a vanished venue only after the resolution concludes *deletion*. The resolution concludes deletion when the user confirms it, or when the user declines the relink, or when the relink fails. Davenport never clears these entries eagerly, for two reasons. First, the map is a crown-jewel field that a rebuild cannot recover. Second, the "deletion" may be a rename that is still resolving. Otherwise, for a *live* record, Davenport surfaces the choice between three options. The options are retract (a local-intent tombstone), unlink (the record continues without a venue), and restore the note from the record. For a tombstoned record those options are nonsense. To delete an orphaned note counts as acknowledgment, because a deletion is a stronger act than the banner click. The tombstone therefore becomes claimant-free and prunable after retention.

An event that leaves the sync horizon (§5.7) is not a deletion. Horizon exit and tombstoning share no code path.

### 5.7 Sync horizon

Each calendar syncs a configurable window via `calendar-query` time-range filters. The default window is the past 3 months and the future 12 months. Backfill beyond the window is on-demand for each calendar. Davenport pulls recurring series that intersect the window whole, and does not clip them.

Membership policy: sync-tokens govern ledger membership, and the horizon governs enumeration and views. `sync-collection` is protocol-unscoped: the server reports the changed hrefs with no regard for any time window. Davenport fetches and applies every reported href. A reported href with no record mints a record, in the horizon or out of it (§5.1). Rationale: the token advanced past the change, so to ignore a reported href discards knowledge that the protocol will not repeat. Which hrefs to ignore is exactly the kind of choice that must not be made silently at implementation time. The initial enumeration is horizon-scoped, so the ledger starts horizon-sized. The ledger grows past the horizon only by three routes: the increments that the server itself reported, the confirmed boundary-crossers of §5.1, and explicit backfill. Feeds are horizon-clipped with an unclipped existence check (§5.2).

This spec accepts and writes down two consequences. First, Davenport retains out-of-horizon records, but excludes them from fallback diffing and from views until the window covers them. These records can go stale. `If-Match` catches the staleness on the next push (§5.5), or the token catches it on the next remote change. This behavior applies the acceptance pattern of §9.5 to the ledger. Second, an event created beyond the future edge and never modified is invisible to the token, because nothing changed since. It is also invisible to the initial enumeration, because nothing intersected. Therefore, when the future edge of the window advances past a granularity (default one day), the engine runs a `calendar-query` over the newly included slice. The engine then mints records for the unknown resources that it finds there. The CTag fallback needs no such step, because its full-window query re-enumerates the slide-ins by construction. The delta query makes token mode do deliberately what the degraded path does by accident.

This spec states the scale envelope, so that implementation knows what to test against. Bounded membership keeps the ledger horizon-sized. A busy calendar at the default window runs to hundreds of records. Several accounts of busy shared calendars run to low thousands of records. Thousands of small markdown files sit comfortably in `metadataCache` and in sync-tool working sets. Determinism plus write-if-changed (§3.2) holds steady-state churn at zero. Tens of thousands of records are outside the envelope, and deep backfills across many calendars produce that number. The levers are per-calendar horizon overrides, backfill restraint, and leaving high-volume calendars unsynced. The magnitudes are verified under load in the test plan.

## 6. Event lifecycle

### 6.1 States

- `state: draft` — the note has event fields. Davenport renders the note on local calendar views. No server interaction occurs. Drafts are a supported planning workflow, and Davenport renders them next to live events.
- `state: ready` — the user signaled push intent. Davenport runs validation. If validation passes, Davenport creates the event on the server and mints a record, and the note becomes live.
- Live — a record exists for the note's `uid`. Later edits follow §5.3 without a new signal. The attendee gate still applies to those edits. Rationale: creation is the dangerous transition, because creation claims a UID and may notify people. Users expect a modification of an already-shared object to propagate.

Any one of these actions writes the same `ready` signal: a "Push to calendar" command, a button on calendar/agenda views, the quick-add confirm (§8.2), or hand-editing frontmatter. Field and command are one mechanism, not two. After a successful push, Davenport removes the `state` key. A missing `state` key together with a present `uid` reads as live, and a permanent `ready` value would be stale text that looks like state.

Davenport does not support a hand-edit of `calendar:` or `type:` on a live note. Each of these two changes implies a delete-and-recreate across collections: a calendar move, or a conversion between event and task. Davenport surfaces the change in Needs Attention and offers a revert. The same guard covers `uid`, in both directions. If an identity appears or changes by a non-plugin write, Davenport surfaces the identity and *never auto-binds* it. Davenport also offers the §3.4-style recovery ("this looks like a copied note — strip to draft?"). §3.4's rationale applies verbatim to the note-side claim. The sharp case is a duplicated note whose original was deleted. Without this guard, the copy would bind to a live shared event and push an un-signaled reschedule. Davenport also surfaces an identity *deleted* by hand, and offers an unlink for it. The self-write exclusion (§5.3) is the discriminator in all of these cases. Rationale: field-and-command equivalence holds for signals. It does not hold for operations with server-side sequences, and it holds least of all for identity. Two hand-edit cells have defined outcomes. First: a hand-edit can re-add `state: ready` to an already-live note. Davenport then strips the key as satisfied, logs it, and does not push again. The identity already exists, and a creation would only 412 into convergence. Second: if a hand-edit adds `state: draft` to a live note, Davenport surfaces the note like other unsupported hand edits. Demotion has server-side legs, so Davenport offers the revert command, and a hand-typed field never triggers a server deletion. A deletion of `calendar:` or `type:` counts as a change to that field. Separately: `ready` executes on any device that observes it, and this behavior does not depend on the dirty set. A note that carries `ready` and `uid` can arrive on a second device by vault sync. That note is executable on the second device, because `If-None-Match: *` makes creation race-safe (§5.5). The device that executes is the device that prompts any attendee gate. §6.2's identity clause gates execution: if a note's identity resolves to a tombstoned or quarantined record, `ready` on that note never executes. The un-cancel gesture must not resurrect such a record.

Execute-anywhere presumes credentials, and credentials may not travel (SecretStorage cross-device behavior is Appendix A item 7). A device that lacks an account's credentials marks that account disabled-on-this-device. The §14.4 card states this status; the user does not discover it through failures. Such a device performs no retries against that account, and it leaves the account's push work and pull work for credentialed devices. This spec also states the designed path for an edit made on an uncredentialed device; it does not leave that path emergent. The dirty entry of such an edit can never push from that device. The edit therefore reaches the server through the note file, which arrives on a credentialed device. On the credentialed device the divergence is not dirty and takes §5.3's grace-surfaced path: a prompt, not an automatic push, and acceptably so. The alternative is to teleport dirty state between devices, and §3.3 prohibits that for cause.

### 6.2 Validation

Validation gates every push. Validation never triggers a push. A push requires all of the following conditions. The `calendar` must resolve and must accept the component type. The note must have a `start` (or `date`), an `end`, `duration`, or all-day end. An `rrule`, if present, must parse. The shape must not contradict itself: `date` alongside `start`, or `end` alongside `duration`, fails and names both keys (§3.1). Enum fields must stay within their vocabularies. The `uid` must not be template-minted, and it must not be a duplicate. The identity must not resolve to a tombstoned or quarantined record. That failure states the reason legibly ("this identity ended in a tombstone; acknowledge the banner first — a later push mints a fresh identity" / "this record is quarantined; resolve it first"). The reason for this rule is that a hand-typed `ready` on an orphaned note is a plausible un-cancel attempt. An execution of that `ready` would resurrect what §5.6 exists to keep dead. Davenport surfaces failures as note-level warnings. The warnings distinguish "not pushed: draft" from "not pushed: invalid," and they name the failing field. Davenport skips nothing silently.

### 6.3 Adoption

First contact with an existing calendar and an existing vault requires linking, not duplication:

- Davenport refuses adoption onto a note that already bears a different identity, and offers venue-linking instead. One note holds one identity slot. To put many events on one note, use the venue mechanism (§7.1), not multiple `uid`s.
- A "link note to existing event" command performs the following actions. It sets the record's venue pointer. It backfills `uid` and `calendar:` into the note (§3.4: resolution requires both keys). It backfills the record's modeled fields into the note's frontmatter, so the post-link diff is empty. It strips any `state` key. The modal previews exactly what will change before the link. The command performs no server write. Rationale for the field backfill: without the backfill, the note's pre-existing fields diverge from the base as soon as the link completes. The pending machinery would then push those stale fields over an existing event — most likely a shared event — without any signal.
- The venue pointer and the materialization map are user-chosen determinism inputs. Therefore, if two devices choose differently, a race starts, and determinism cannot resolve that race. Different choices are different inputs. The sync tool's file resolution would otherwise discard one user's action silently. It would discard that action on exactly the fields that a rebuild cannot recover. The rule in v1 is detection, not merge. If a differing arrived value supersedes a device's own pointer write or map write, that device surfaces the mismatch. The device names both candidates for the user to pick. This spec prohibits silent last-writer-wins here, as it does everywhere.
- On the first sync of a calendar, Davenport suggests fuzzy matches between unlinked records and unlinked event-shaped notes. The match uses title proximity and date proximity. Davenport offers the suggestions and never applies them automatically.

### 6.4 Retraction

Three distinct commands exist, and all three tombstone the record. The first command deletes the note and the event. The second command reverts the note to draft. Davenport deletes the event, the note keeps its event fields, Davenport strips `uid`, and Davenport writes `state: draft`. A later push then mints a fresh identity, because the old identity ended in a tombstone. The third command removes the event from the calendar and keeps the note: Davenport deletes the event and strips `uid` and `state`.

## 7. Venues and routing

### 7.1 Model

A record can point at a venue. A venue is a note, or a note plus a section, that holds the event's meaning. The venue does not enumerate its events. Calendar views, agenda widgets, and "linked events" panels are projections, and each projection queries the ledger for records that point at the venue. One venue may receive many unrelated events; one example is a running 1:1 note for each person. "Linked," wherever this spec uses the word, means *mutual claim*. Mutual claim means that the record's pointer targets the note *and* the note's `calendar:`+`uid` resolve to that record. A pointer without a reciprocal claim is venue-routed or dangling. Davenport then does a record-only apply (§5.4) and never writes to the note. This rule is the operational discriminator between the pointer's two roles. It also stops a stale pointer from writing another event's fields into the wrong note. One example of a stale pointer is §10.4's old record, which aims at a note that now claims the successor identity. Rationale: per-event frontmatter arrays on shared notes churn the file at every reschedule, and body-embedded event syntax makes prose a sync surface. Both designs were rejected.

### 7.2 Routing

Inbound events find venues by precedence:

1. Explicit assignment: a drag onto a note, or the picker modal.
2. Rules: predicates over calendar, summary pattern, and attendees, mapping to a venue and a materialization template. Attendee predicates resolve through the person-note index (§8.4). Rules may live in settings, or in the venue note's frontmatter as a claim block ("this note claims events matching X"). Note-resident claims keep the configuration next to its subject, and claims evaluate before settings rules, because the more specific declaration wins.
3. No match: the inbox. The inbox holds records without venues. The agenda/inbox view lists those records, and the user can materialize them on demand.

### 7.3 Materialization

Materialization is lazy: a pull of an event creates a record, not a note. Davenport creates notes and sections when the user opens the event, or when the user runs an explicit materialize command. Rationale: eager scaffolding fills the vault with hollow notes for meetings where no one takes notes.

Each rule sets its own materialization target. The target is either a new note from a template (§8.1), or a dated section that Davenport appends to the venue note from a section template. The record stores what Davenport materialized, including a content hash of the created note taken at materialization. That hash is the untouched discriminator for §5.4's remove option. Materialized content belongs to the user immediately. If the event later moves, the record updates, and any date rendered into the section heading goes stale. This spec accepts and documents that staleness: written content about a meeting that then moved is a historical artifact. Live-rendered inline time widgets are a possible later alternative to static interpolation. Sync never updates static interpolation into prose.

### 7.4 Daily notes

The daily-note integration has two parts. The first part is a routing rule whose venue is date-matched, not attendee-matched. The second part is a codeblock that the user's daily-note template can call to render the day's events with a configurable line format. If the user materializes into a date-matched venue that does not exist yet, Davenport creates the daily note through the daily-notes core plugin's settings. Davenport does not own daily-note rendering.

### 7.5 Venue deletion semantics

After a remote cancellation of an event, the record gains a remote-observed tombstone (§5.6). The materialized sections stay, and they can carry an optional annotation. After a deletion of the venue note, the records lose their pointer and fall back to routing or to the inbox. No server write occurs. The venue was authoritative for narrative, not for existence.

### 7.6 Scoped quick-add

If the user invokes quick-add from a venue note, quick-add inherits that note's claim-rule context: calendar, attendees, template, and venue link.

## 8. Templating

### 8.1 Inbound templates

Materialization templates interpolate event fields: `{{summary}}`, `{{start}}`, `{{end}}`, `{{attendees}}`, `{{location}}`, `{{description}}`, `{{conferenceUrl}}`, `{{calendar}}`, `{{date}}`. Davenport parses `conferenceUrl` from conference-related `X-` properties and from the description contents, because providers place meeting links inconsistently. Each routing rule selects its template, and each calendar supplies a default template.

Templates fire once, at materialization. Materialization always writes an explicit `summary` key (§3.1: Davenport never re-evaluates filename-derived titles for live notes). Materialization also always writes an explicit `calendar:` key (§3.4: note→record resolution requires that key). The §6.3 supersession rule governs materialization-map writes. If a differing arrived value overwrites a device's map entry, that device surfaces the mismatch. The device does not accept silent last-writer resolution. Sync never re-renders template output. Templates must not set `uid` or `state: ready`.

### 8.2 Outbound: event types and quick-add

Event types are user-defined presets. A preset holds a default duration, a calendar, a `type`, a recurrence, an alarm, `class`/`transp` defaults, expected fields, and a body template. Expected fields supply validation ("this 1:1 has no person"), and they make typed events queryable.

Quick-add uses `chrono-node` to parse natural language ("lunch with Sam tuesday 1pm"). Quick-add puts the result into a pre-filled confirm modal, and the event type sets the type of that modal. The confirmation in the modal is the `ready` signal. Quick-add never writes to the server without the modal.

### 8.3 Template engine posture

Davenport implements plain `{{field}}` interpolation, so Davenport works standalone. If the user installs Templater, templates may be Templater templates, and Davenport passes the event context as arguments. Davenport does not implement conditionals, loops, or its own scripting. Rationale: a bad reimplementation of Templater and a hard dependency on Templater are both known failure modes. The two-tier approach avoids both failure modes.

### 8.4 Person notes

Davenport derives attendee identity from the vault, and does not store it in configuration. A person note declares its addresses in frontmatter, in an `email:` key or an `emails:` list. The key name is configurable, and the default key name is `email`. Davenport indexes the notes that carry the key through `metadataCache`, and the user can scope the index to a folder. Rationale: the identity of a person belongs to the vault; the vault versions that identity, and the user edits it where the person lives. Venue claim blocks follow the same principle. A derived index also removes a settings table that a user would otherwise maintain by hand forever.

The index serves inbound templates (`{{attendees}}` renders matched addresses as links), routing predicates (§7.2), scoped quick-add (§7.6), and outbound attendee resolution. In outbound attendee resolution, a `[[Jane Doe]]` name on an event supplies her address for `ATTENDEE`, subject to the attendee gate. Davenport renders unmatched addresses as plain text, and offers a "create person note" action in the agenda context menu and in the note context menu. If two notes claim one address, Davenport detects and surfaces the conflict, like duplicate UIDs (§3.4).

The user's own addresses come from the account principal's `calendar-user-address-set` at discovery, and each account has a manual fallback. Davenport needs those addresses to locate the user's `ATTENDEE` entry for RSVP (§12). CardDAV integration remains out of scope (§17). CardDAV could later populate person notes; it would not replace them.

## 9. Description and attachments

### 9.1 Direction

Davenport projects `DESCRIPTION` and `ATTACH` in one direction only: from the vault to the server. Davenport renders both properties at push time. Davenport never merges a remote edit to these two properties back into the markdown. The ownership mode decides the treatment of a remote edit: Davenport flags the edit, or Davenport overwrites the edit. Rationale: Davenport cannot merge a rendered description back into its markdown sources. Also, a bidirectional note body would make all prose a sync surface.

### 9.2 Description sources

Each calendar selects one of these description sources. An event type can override the selection of the calendar.

1. The `description:` frontmatter field. This source is the global default for every calendar. The field is explicit and small, so it is safe in all conditions.
2. A delimited body region. The region is the content below a configurable heading. The default heading is `## Description`. This source is a per-calendar opt-in. It is suitable for personal calendars.
3. The whole body. This source is opt-in only. When the user enables it, Davenport shows a warning: on a shared calendar, every attendee can read the description.

Independently of the description source, a per-calendar option appends an `obsidian://` backlink to the note. The option puts the backlink in the `URL` property, or in a description footer. The backlink contains the vault name and the note name. On a shared calendar, attendees can read both names. Therefore this option carries the same visibility warning. Filenames are content.

### 9.3 Embeds

Description rendering resolves `![[File]]`, `![[File#Heading]]`, and `![[File#^block]]` with `metadataCache`. Davenport strips the frontmatter of each embedded file. Davenport applies a recursion depth limit, and it detects cycles. Davenport converts the markdown down to plain text, because `DESCRIPTION` is text. Davenport strips the formatting. Davenport applies two mappings: `[text](url)` → `text (url)`, and wikilinks → plain names or `obsidian://` URIs, as the setting specifies. `ical.js` performs the escaping and the line folding. An HTML alternative in `X-ALT-DESC` is optional, and Appendix A item 4 gates it. Davenport promotes a media embed, for example `![[diagram.png]]`, to an attachment (§9.4). Davenport then leaves a `(attached: diagram.png)` placeholder in the text. Davenport omits nothing silently.

### 9.4 Attachments

The `attachments:` list maps to `ATTACH`. Davenport uses one mechanism for each entry:

1. External URL → `ATTACH;VALUE=URI`.
2. Vault file, and the server advertises RFC 8607 managed attachments → POST the file. The server then hosts the file and rewrites the URI. Davenport probes for this capability at discovery. Davenport never assumes the capability (Appendix A item 3).
3. Vault file, in all other conditions → inline `ATTACH;ENCODING=BASE64;VALUE=BINARY`. Davenport sets `FMTTYPE` from MIME detection, and Davenport sets `FILENAME`. A configurable size cap applies. A file that is larger than the cap fails validation, and the message names the file. Rationale: an inline attachment travels with the event on every fetch by every client, and inline attachments hit the server size limits.

Attendees receive the attachments. The shared-calendar warning in §9.2 covers attachments explicitly.

Davenport treats an inbound `ATTACH` as follows. Davenport renders a URL attachment as a link in the materialized content. Davenport offers an inline binary as a save-to-vault action. Davenport never writes an inline binary automatically.

### 9.5 Snapshot semantics

Davenport renders the derived content at push time, from one file or from many files. The record stores a hash of each rendered output. At sync time, change detection makes a fresh render and compares it against the stored hash (§5.3). If an embedded source changes after the push, Davenport does not re-push automatically. A "refresh description/attachments" command re-renders the content and pushes it on demand. On an attendee-bearing event, this push is a gated write (§5.5). An optional re-render also occurs on lifecycle transitions. Rationale: a dependency-triggered auto-re-push needs an embed build graph, and it generates "event updated" noise on the calendars of the attendees. Eager freshness is the wrong default for shared events. The user-facing documentation states the snapshot behavior.

## 10. Tasks and time blocks

### 10.1 Types

`type: event` — a fixed time and an external commitment. It maps to VEVENT. `type: task` — a deadline with flexible scheduling. It maps to VTODO (`due` → `DUE`, `start` optional, `completed`, `priority`, subtasks later via `RELATED-TO`). `type: block` — time that the user claims for a task. A block is a VEVENT, and its `task:` key links the task note that the block serves. When the user completes a block, Davenport offers to mark the task of that block complete. This is an offer, not an automatic write, because the end of a block does not prove that the work is done.

### 10.2 Targets

Davenport pushes a task only to a collection whose `supported-calendar-component-set` includes VTODO. Discovery lists the task lists as first-class registry entries. A push of a task at an events-only calendar fails validation. The message names the mismatch, and it offers the block fallback: schedule the work time of the task as a VEVENT. Rationale: iCloud reminders and Google tasks are unreachable (§2.1). Time blocks are the workflow that routes around both silos. Time blocks also stand on their own (drag task to calendar → block; completing the block completes the task).

A per-calendar option materializes task deadlines as all-day events on an events-only calendar.

### 10.3 Completion

The frontmatter holds the completion of a task note (`completed` timestamp; `status` mapping to `COMPLETED`). Inbound completion from other VTODO clients updates the frontmatter. Checkbox-line integration (Tasks-plugin syntax) is a later, explicit opt-in. This opt-in declares specific lines as a sync surface. The base design does not contain it.

### 10.4 Transmutation

"Convert task to event" and "convert event to task" are commands. The roadmap contains them again, because their design is no longer transactional. The original specification treated conversion as an atomic ordered sequence. That sequence was the only online-only, out-of-loop server writer in the spec. Two review rounds found costs in it, and every one of those costs came from that framing. The atomicity protected against entanglements: resurrection, misread deletions, and identity confusion. The current machinery removes these entanglements independently. Therefore the operation decomposes into two ordinary, idempotent engine behaviors, and these two behaviors have no required order:

The convert command first pre-validates the rewritten form per §6.2, before it writes anything. The pre-validation includes component-type acceptance at the target collection, which is the likely failure. The command then executes entirely locally and makes no server calls. It writes in a mandated order. First it writes the local-intent tombstone on the old record, annotated with the successor identity ("converted to (collection, uid)"). Second it writes the note rewrite as a plugin self-write: new `type`, remapped fields (`start`↔`due`), target `calendar:`, freshly minted `uid`, and `state: ready`. The rewrite carries the venue pointer forward as the input of the new record. The order is load-bearing. A crash between the two writes leaves an orphaned note, and the "converted" banner of that note names a successor identity. An annotated successor that resolves to no record and to no claiming note is a *detectable* incomplete conversion. The standard flight grace applies first, because the successor note may be a file that is still in transit from another device. After that grace, Davenport surfaces the incomplete conversion and offers two actions (row 13b). The first action is complete: Davenport re-derives the rewrite, which is mechanical from the base of the record. The second action is revert. Where the resource survives, revert is the §5.6 keep path. Where the `DELETE` already fired, revert is a fresh push of the old data, and Davenport states it as such. The reverse order has no detector. A rewritten note beside a live old record is indistinguishable from ordinary venue routing (§7.1 — a pointer without a reciprocal claim is legitimate). The half-completed conversion would then linger silently, with the old event alive. The server work then happens as standard engine behavior. §5.6 tombstone processing deletes the old event. §6.1 push creates the new event. Rationale for why this is sufficient: every intermediate state is an already-specified state ({new identity ready or live} × {old tombstoned or pending}). The mandated order makes the one crash-reachable intermediate a surfaced state, not a silent state. Both artifacts are files. Therefore an offline conversion queues by its existence, and it executes wherever it is first observed (M9 semantics, race-safe via `If-None-Match: *` and 404-on-DELETE). A device can observe the server deletion first. That device writes a remote-observed tombstone. The annotated local-intent tombstone then arrives and upgrades that tombstone by monotone dominance. The upgrade corrects the banner to "converted, not cancelled". The §6.1 hand-edit guard does not fire, because the rewrite of the command never enters the dirty set. Each half of the "inconsistent" intermediate state is acceptable on its own. Both halves must happen at some time, but they do not have to happen at the same time.

There are three boundaries. First, attendee-bearing events refuse conversion. Under any order, a conversion generates `CANCEL`-plus-reinvite mail to every attendee, and no decomposition changes this. Second, a `412` on the `DELETE` of the tombstone surfaces one prompt: retract anyway, or keep both. Such a `412` means that the old event changed remotely after the user converted it. Third, the command requires a linked note. A venue-routed record has no place to hold the successor identity between the command and the creation.

Calendar moves share the decomposition. "Move to calendar…" keeps the same component type and changes the collection; it is the `calendar:` cell of §6.1. This command has the same shape as the conversion command, but without the field remap. The command first pre-validates at the target: component-type acceptance, and a resolvable registry entry. The command then executes entirely locally, and it writes the tombstone first. First it writes the local-intent tombstone on the old record, annotated "moved to (collection, uid)". Second it writes the note rewrite as a plugin self-write: new `calendar:`, freshly minted `uid`, `state: ready`, and every other field untouched. The rewrite carries the venue pointer forward. Every property of the conversion design carries over verbatim. The row-13b detector reads the annotation, because "moved" and "converted" are one mechanism. The crash windows and their surfaces are identical. Offline queuing and cross-device tombstone convergence hold. A linked note is necessary for the same reason: the note holds the successor identity between the command and the creation. The command mints a fresh identity, and it does not carry the old identity forward. §6.4 already rules that Davenport does not reuse an identity that ended in a tombstone. Also, a carried UID in the target collection would be indistinguishable from the deliberate cross-collection UID reuse of iTIP. Such a UID would degrade the inbound pairing of §5.6, which must continue to tell an observed move apart from an invited copy. Attendee-bearing events refuse the decomposed move exactly as they refuse conversion, because a delete-plus-recreate is `CANCEL`-plus-reinvite mail. Some servers support WebDAV `MOVE` within a calendar home. `MOVE` can later serve as an atomic same-type move, and it may avoid scheduling side effects. Appendix A item 26 holds two questions: do the providers support `MOVE`, and does `MOVE` stay silent to the attendees? Until these two points are verified, the refusal stands unconditionally. `MOVE` is a recorded-fact optimization, not a v1 dependency.

## 11. Recurrence

One note or one record represents a recurring series. `rrule` stores the rule. Davenport computes the instances for display. A record of a series carries a materialization map (instance date → materialized note/section). This map tracks the per-instance notes, and Davenport needs no per-instance records.

v1 supports whole-series edits only, and it has one closure rule. Davenport refuses a series edit to the `start` time, to `rrule`, or to `timezone` while the base contains overrides or exclusions. Davenport also refuses the conversion of a timed series to all-day, and the conversion back, while the base contains overrides or exclusions. The schema expresses that conversion as a key swap (`start` ↔ `date`), not as a value edit. Davenport states the reason for each of these refusals. Rationale: a patch of the master under existing `RECURRENCE-ID`s orphans those overrides. An orphaned override then targets an instance that no longer exists. This produces ghost or duplicated instances on other clients, and wrong rendering in Davenport's own views. A rewrite of the exceptions to match is precisely the exception-editing machinery that v1 defers. A drop of the exceptions destroys the moves of other people. Series edits to fields that do not shift instances (summary, description, alarm, categories) patch safely. Davenport preserves per-instance overrides and exclusions round-trip (§5.5) from day one. They become editable in a later stage, and that stage represents them as explicit exception entries alongside the series. Davenport must also *render* the preserved overrides. A view computes the instances from the RRULE. The view then applies the existing overrides and exclusions read-only. Preservation without display would show wrong times for exactly the instances that someone deliberately moved. Recurring VTODOs follow the complete-and-respawn client convention. Davenport stores `TZID` faithfully. Davenport computes all-day instances and DST-straddling instances in the zone of the event, not in the zone of the device.

## 12. Invitations and RSVP

Inbound invitations are events where the user is an `ATTENDEE` with `PARTSTAT=NEEDS-ACTION`. To identify the attendee entry of the user, Davenport matches the entry against the own addresses of the account. The own addresses of the account come from §8.4: `calendar-user-address-set` from principal discovery, manual per-account fallback. The match normalizes the case and strips the `mailto:` prefix. The user can add more aliases to the per-account fallback list. Without these aliases, intermittent RSVP misidentification on real servers is guaranteed. Materialized notes and agenda entries for such events show a pending banner.

A response is a server action, not a field edit. A write of `PARTSTAT` informs the organizer; on a scheduling server this write is an iTIP reply. Davenport therefore confirm-gates the response, as it confirm-gates all attendee-touching writes.

Primary UI: Accept / Decline / Tentative buttons on the agenda sidebar and on the note banner. A button confirms and pushes in one gesture. The underlying mechanism is the `rsvp:` frontmatter key. A hand edit of this key is an equivalent signal. Davenport validates the hand edit against the enum, and it confirm-gates the hand edit identically. A Properties-panel dropdown is a progressive enhancement only, because no official property-widget API exists (§2.2). The buttons-plus-field layering is the foundation for every synced enum (`rsvp`, `status`, task status, `class`).

## 13. Property mappings

- `alarm: -15m` → `VALARM` (DISPLAY, TRIGGER relative). While Obsidian is open, Davenport fires in-app notices for the alarms. The native client does the background delivery (§2.2).
- `categories` ↔ `CATEGORIES`. Davenport can also map the categories to Obsidian tags, with a configurable prefix and a per-calendar direction. An inbound tag write touches only the prefixed tags: it makes a union under the prefix, and it replaces within the prefix. An inbound tag write never adds, removes, or reorders a tag outside the prefix. Users own the `tags:` key heavily, and this mapping is the one mapping that writes into non-Davenport frontmatter.
- `transp` → `TRANSP`. Blocks default to `OPAQUE`. Event types may set the defaults.
- `class` → `CLASS` (`public`/`private`/`confidential`). Event types may set the defaults. This mapping pairs with the privacy warnings of §9.
- `status` → event `STATUS` (`tentative`/`confirmed`/`cancelled`). `status` is distinct from `state` in the key, the vocabulary, the code identifiers, and the documentation.
- `location` → `LOCATION`. Davenport preserves the structured location `X-` properties, but it does not model them.

Unmodeled properties are governed by the round-trip rule (§5.5).

## 14. Interface

### 14.1 Scope

Davenport's interface serves its workflow: planning drafts, materializing notes, responding to invitations, scheduling blocks, and supervising sync. The interface does not compete with dedicated calendar clients on rendering features. Every view is a projection of the ledger and the drafts. No view holds state that the ledger and device-local storage do not hold. Rationale: a stated non-goal prevents the calendar view from absorbing effort that the sync engine needs.

### 14.2 Calendar view

The calendar view is a workspace leaf with month, week, and day modes. The rendering library is FullCalendar.js or an equivalent library. The library is an implementation choice, not a spec commitment.

The view displays events from selected calendars, drafts, blocks, and task deadlines. Task deadlines are a per-calendar option. The view gives each calendar its own color. The view shows drafts dashed, `status: tentative` faded, `status: cancelled` struck, and blocks patterned. The view shows badges for a pending RSVP, a conflict, and a validation failure. The set of visible calendars, the current mode, and the current date are device-local view state.

Interactions:

- Click an event: the view opens its materialized note. If the event has no materialized note, the view offers materialization. Click a draft: the view opens its note.
- Drag on empty space: the view opens quick-add (§14.6). The view pre-fills quick-add with the selected time and with the view's calendar context.
- Drag or resize an event: the view edits `start`/`end` through the standard edit path. The standard edit path includes the debounce, the validation, and the attendee gate. The view disables this interaction on remote-owned calendars. On an attempt, the view shows the reason. The view does not silently remove the handle.
- Context menu on an event: the menu shows open or materialize note, assign venue, push (for drafts), retraction options, convert to task or event, RSVP actions, join meeting, and reveal record.

### 14.3 Agenda sidebar

The agenda sidebar is a right-sidebar leaf. It is the working surface for the day. The sidebar sections are in this order:

1. Needs attention — this sidebar section lists every state that the spec routes here, and each listed state has a resolve action: conflicts (§5.4), validation failures (§6.2), dangling pointers (§5.6), grace-period divergence (§5.3), remote-owned divergence (§4.2), hand-edited `calendar:`/`type:`/`uid` (§6.1), persisting uid-without-record (§3.4), quarantined records (§3.2), duplicate address claims (§8.4), and pointer/map supersession mismatches (§6.3), orphaned-note acknowledgments and move suggestions (§5.6), and suspended-note notices (§3.2, Appendix B). Note banners (§14.5) are the per-note rendering of the same conditions. Every bannered condition also lists in this sidebar section, so problems in closed notes stay discoverable. An item dismisses itself when its underlying condition resolves. Self-dismissal is mandatory for the flight-skew items. The designed resolution of a flight-skew item is a late-arriving file, not a click. A stale prompt that outlives its problem is the same trust failure as a problem that nobody surfaces. Preservation items (§4.2, §5.4) are the stated exception. A preservation item records a historical displacement, and it has nothing to resolve to. A preservation item therefore resolves by acknowledgment, and it carries the displaced values until that acknowledgment. This sidebar section is present only when it is non-empty, and it is always first. Rationale: the trust surface fails if problems live in a view that nobody opens.
2. Needs response — this sidebar section lists pending invitations. Each invitation has inline Accept, Decline, and Tentative actions.
3. Today and upcoming — this sidebar section is chronological and shows a configurable number of days ahead. The sidebar section has inline join and open or materialize actions.
4. Inbox — this sidebar section lists unrouted records (§7.2). The sidebar section has assign-venue and materialize actions.

### 14.4 Sync activity view

The sync activity view is the home of the trust surface. It ships with the first write-capable release. Each account has a card. The card shows the connection status and the credential status ("no credentials on this device" is a per-account state, §6.1), the last sync time, the count of changes that await push (the count is derived, §5.3 — there is no queue), and a pause toggle. The sync log is below the cards. The sync log is a filterable table of operations (time, calendar, item, action, outcome, reason). The table includes refusals, skips, and conflicts, not only successes. The view has these actions: sync now, dry-run per calendar ("would update 3, delete 1" with an expandable item list), and global pause. Davenport takes local snapshots of the affected records and notes before a destructive batch. The view lists these snapshots for restore. Rationale: a sync engine earns trust in its first month, or it never earns trust. Demonstrability requires a place to look.

### 14.5 Status bar, banners, codeblocks

- Status bar item (toggleable, device-local): the item shows the next event with a countdown. The click menu has these entries: join meeting, open agenda, and sync now.
- Note banners: these banners are rendered UI and never file content. The banners are pending invitation (with RSVP buttons), conflict, validation failure with the failing field, and remote-deleted flag.
- Codeblock views: a `davenport` fenced block holds YAML parameters — `view` (agenda | day | week | month | list), `calendars`, `venue`, `from`/`to`, and `format` (line template for list/agenda). The rendering is read-only and has click-through to notes. The daily-note integration (§7.4) is this mechanism.

### 14.6 Modals

- Quick-add: Davenport parses the free-text input live (§8.2). The modal shows a structured preview of the resulting fields, an event-type picker, a calendar picker, and a confirm button. The confirm button is the `ready` signal. Esc always abandons quick-add cleanly.
- Attendee-write confirmation: this modal shows what changes and who will be notified. The modal shows this before any write that triggers scheduling messages. This modal is not suppressible (§15.4).
- Retraction chooser: this modal shows the three §6.4 options. Each option states its consequences.
- Adoption picker: this modal shows a searchable list of unlinked events for "link note to existing event." The modal pins fuzzy-match suggestions on top.
- Venue picker: this modal shows a searchable list of notes. Use this modal to assign a record's venue.
- Conflict resolution: this modal shows a field-by-field table of local values and remote values. Pick a value for each field, or take one side wholesale.
- Dangling-pointer resolution: this modal offers retract, unlink, and restore (§5.6).

### 14.7 Command inventory

Conventions: command names use verb-first sentence case (Obsidian prefixes the plugin name). Context commands appear only when they are applicable (`checkCallback`). Commands have no default hotkeys. Every command is a thin verb over behavior that the spec specifies elsewhere. Commands introduce no behavior of their own.

Global:

- Sync now — this command syncs all calendars (§5.1).
- Sync calendar… — this command shows a picker and syncs one calendar.
- Preview sync (dry run)… — this command shows a picker. The command renders the §14.4 preview and writes nothing.
- Pause/resume syncing — this command is a global toggle. The per-calendar pause lives in §14.4.
- Quick-add event — this command opens the §14.6 quick-add.
- Open calendar / Open agenda / Open sync activity.
- Backfill calendar history… — this command shows a picker and a date range (§5.7).
- Export calendar to ICS… / Import ICS file… (§16).

Active note (these commands are visible when the note qualifies):

- Make this note an event… — this command shows an event-type picker. The command inserts the typed fields. The command sets `state: draft`. The command makes no server contact.
- Push to calendar — this command sets `state: ready`. The validation and the push follow (§6.1–6.2).
- Link to existing event… — this command opens the adoption picker (§6.3).
- Unlink from event — the record keeps the event. The record loses the venue pointer.
- Revert to draft / Remove from calendar (keep note) / Delete note and event — these commands are the §6.4 retractions.
- Refresh description and attachments — this command re-renders the derived content. The command pushes the derived content (§9.5).
- Convert to task / Convert to event — these commands perform transmutation (§10.4). These commands refuse on attendee-bearing events.
- Move to calendar… — this command shows a picker. The command performs a same-type move through §10.4's decomposition. The command refuses on attendee-bearing events.
- Accept invitation / Decline invitation / Respond tentative — §12 specifies these commands. These commands are visible only with a pending `PARTSTAT` or a changeable `PARTSTAT`.
- Reveal on calendar — this command opens the calendar view. The calendar view centers on this event.

Selection context (calendar or agenda focus): these commands are available — Open or materialize note; Assign venue…; Join meeting.

### 14.8 Materialized filenames

Davenport sanitizes the note filenames that come from summaries. Davenport replaces the illegal characters of each platform. Davenport caps the length. Davenport adds a suffix on a collision. A per-calendar option renames notes when the remote summary changes, and the default for this option is off. Rationale: renames churn links and vault sync. The record decouples the title from the identity anyway.

## 15. Configuration

### 15.1 Placement rules

Davenport has three storage tiers. Every configurable item belongs to exactly one tier. The choice of tier depends on whether divergence across devices is acceptable:

- Synced settings (`data.json`): semantic configuration that must agree across devices. This tier holds accounts (minus secrets), the calendar registry and per-calendar options, event types, routing rules, and global defaults. Rationale: if two devices disagree about routing rules or ownership modes, the two devices produce divergent vaults. Davenport does not store the person index at all. Davenport derives the person index from vault frontmatter (§8.4). `data.json` travels only when the sync setup carries it (§2.2). Therefore Davenport verifies settings agreement and adds a tripwire for it. Davenport never assumes settings agreement. Onboarding includes a settings-sync check under the user's own setup. At runtime, every settings write also writes a settings-revision marker. The marker is a small markdown file beside the ledger. Its default path is `davenport/settings-revision.md`. This path is outside the records folder, so the quarantine scanner never sees the marker. The marker carries a monotonic revision and per-section hashes (accounts, registry, event types, routing, defaults). Markdown syncs unconditionally. Therefore a device whose local revision trails the marker knows that its settings channel is broken. The device surfaces exactly that condition, and it names the sections that disagree. The device calls out ownership-mode divergence specifically, because ownership-mode divergence is the most dangerous configuration split that the system permits. The marker is advisory. The marker gates nothing. If a merge damages the marker, the worst cost is one wrong warning, and the next settings write corrects that warning. Pre-stated branch: if Appendix A item 22 verifies badly across common setups, the escalation is to move the registry into the vault. That move puts the registry under record-style treatment (deterministic emission, checksum, quarantine). This escalation is a v2 design change. The spec records the change here, so that a bad verification lands on a branch and not back on the drawing board.
- Device-local (`saveLocalStorage`): display and session state where divergence is correct. This tier holds the visible calendars, the view mode and date, the status-bar toggle, the pane layout, the log verbosity, and the §3.3 sync cursors.
- In vault: templates (files in the configured template folder), venue claim blocks (§7.2), and the record ledger. Rationale: content that users edit as text belongs in the vault. The vault versions that content together with its other files.

Secrets are the fourth tier (§4.3). Secrets never appear in any of the three tiers above.

### 15.2 Settings organization

Davenport organizes plugin settings into sections. Each item states its default.

- Accounts — add/edit/remove; server URL, username, credential type and entry (§4.3–4.4); test-connection button; re-run discovery.
- Calendars — the registry (§4.1). Per calendar: friendly name, color, ownership mode (default remote-owned), default timezone, default materialization template (§8.1), description source mode and backlink option (§9.2), categories↔tags mapping (§13), remote-deletion behavior (§5.4), remote-edit handling on vault-owned calendars (§4.2), rename-on-retitle (default off, §14.8), task-deadline materialization (§10.2), sync-horizon override, auto-push-on-valid (vault-owned only, default off).
- Event types — list editor: name, component type, default duration/calendar/recurrence/alarm/`class`/`transp`, expected fields, template (§8.2).
- Routing — ordered rule editor: predicates over calendar/summary/attendees → venue, template, materialization target (note vs. section) (§7.2–7.3). The Routing section documents note-resident claim blocks.
- People — derivation settings only (§8.4): frontmatter key name (default `email`), optional folder scope, unmatched-attendee behavior, and per-account own-address fallback for RSVP identity.
- Templates — template folder path; Templater integration (auto-detected, overridable); wikilink render mode for descriptions (§9.3).
- Storage — records folder path (default `davenport/records/`, and the paragraphs after this list state the rules of that path); a button that adds the records folder to Obsidian's excluded files; tombstone and snapshot retention windows.
- Sync — global interval; edit debounce; grace period for unexplained divergence (§5.3); sync-horizon defaults; attachment size cap; embed depth limit.
- Appearance — week start, 12/24h, agenda days ahead, status bar toggle (device-local), draft/badge styling toggles.
- Advanced — log verbosity (device-local), reset device-local state, re-run first-sync adoption suggestions.

The records folder path carries rules that no other item of this section carries. A change of that path moves files. A change of that path also moves the boundary that §5.3 reads. The paragraphs below state these rules.

A change of the setting refuses a target folder that holds a user file. Davenport reads the target folder and every folder inside the target folder, and the scan sees vault files only. The scan passes over a file of the operating system and over a file that a sync tool keeps for itself, because such a file is not a vault file. A file in the target is a record of Davenport when the file parses as a record under the schema of §3.2. The checks of §3.2 then decide whether Davenport quarantines that record, and a record that Davenport quarantines is still a record. Every other vault file in the target is a user file, and one user file is enough for a refusal. This test reads a candidate folder that a settings change proposes, where a file that fails to parse is a user file; §3.2 states the other context, in which such a file in the standing records folder is a damaged record that Davenport quarantines. The settings-revision marker of §15.1 does not parse as a record, so a target folder that holds the marker is refused. That result keeps true the fact that §15.1 states: the marker stands outside the records folder.

Rationale for that definition: Davenport reads the identity of a file, and Davenport reads no intent. A file that does not prove that Davenport wrote it belongs to the user. The test asks for the outcome of §3.2 and not for two checks of §3.2 alone, so §3.2 stays the one authority on the question of whether a file is a record. A conflict copy of a record keeps the bytes of the record under another name. Such a copy passes the self-checksum, fails the name check, and quarantines. Such a copy is a record of Davenport, and it is not a user file. The cost of the refusal is a target that the user resolves by hand. The cost of the opposite rule is a folder of user notes that leave note handling with no warning.

A refusal gates a change of the setting, and a refusal gates nothing else. Davenport runs no check against the folder that the setting already names, so the scan runs on an action of the user and never at the start of the plugin. A file that arrives in the records folder after the change is never a refusal. A record there that fails a check of §3.2 goes to quarantine, and a user file there is inert (§5.3). Rationale: a vault that syncs delivers a conflict copy at any moment, and §3.2 treats such a file as routine and survivable. A standing refusal would make that routine event a halt. It would also halt a second device that reads the ledger of the first device for the first time, because that device takes the folder as it stands and changes nothing.

A change of the setting refuses a target folder that nests with another configured path, and the refusal covers both directions. The records folder must hold no other configured path, and no other configured folder must hold the records folder. Two paths that are equal nest in both directions, and the refusal covers that case. Davenport owns three other settings that name a path in the vault. The first is the template folder of this section. The second is the folder scope of the person index (§8.4). The third is the venue note that a routing rule names (§7.2). Each of these three settings refuses a value that nests with the records folder, and that refusal is the second gate. Without the second gate a user reaches the same damage from the other direction, and the first gate never sees the change. A folder setting that holds no value names no folder, and such a setting takes no part in this check.

Davenport does not own the folder of the daily notes, because that folder is a setting of the core plugin (§7.4). Davenport cannot refuse a value of a setting that Davenport does not own. Davenport therefore surfaces the condition when Davenport observes it, and the two conditions are these: the daily-note folder stands inside the records folder, or the daily-note folder holds the records folder. This spec states a refusal only where Davenport holds a gate.

The records folder is never the vault root. Rationale for the nesting rule and for the vault-root rule: another configured path inside the records folder loses every file of that path to the exclusion of §5.3. The records folder inside another configured folder gives records to a consumer that expects notes. The vault root holds every file of the vault, so the vault root as the records folder gives every file of the vault to the exclusion of §5.3. The vault-root rule stands on its own, because a vault where every folder setting holds no value has no nesting to find.

A change of the path moves the record files of Davenport to the new folder. The move takes every file that the ledger index holds, and it takes every file that the quarantine holds (§3.2). The move carries the bytes of each file without a change, so two devices that hold one record still hold identical bytes (§3.2). Davenport writes no record while a move runs, so no record file arrives in the old folder behind the move. Davenport writes the new value of the setting only after every file arrives in the new folder. The readers of records then read the new folder, and these readers are the ledger index and the quarantine scanner (§3.2). A file in the old folder that the ledger index does not hold and the quarantine does not hold stays in the old folder. §5.3 states what Davenport does with such a file after the move.

A move that fails leaves the setting unchanged, and Davenport reports the failure. The report names the file that failed. Davenport then moves back each file that it already moved. Where a move-back also fails, the report names the path of each record that stands in the new folder. Such a record is a question that Davenport surfaces, and it is not a loss. The reason is that a record holds its identity in its name and in its bytes (§3.2). A scan of the folder that the setting names reads the records of that folder and builds the index from them. That scan is not the rebuild of §3.2, and it needs no request to a server.

A crash stops a move, and no report follows a crash. The setting keeps its old value, and part of the ledger can stand in the new folder. §5.3 holds those files outside note handling, because a record is a record in every folder. Davenport surfaces each such file that it meets. A later pull can mint a fresh record for one of those identities in the folder that the setting names. The surface names the identity of each file that it reports, so a user can see two files of one identity as one question.

The path is synced configuration, so a change of the path writes the settings-revision marker (§15.1). A device that does not receive the new path keeps the old path, and the stale-settings condition of §15.1 is the surface for that device. Davenport never reads an empty records folder as a set of deletions, and Davenport mints no tombstone from an empty records folder (§5.6). The excluded-files setting belongs to Obsidian. A path change does not change that setting, and the button of this section adds the folder that the setting names (§3.2).

### 15.3 Override pattern

Behavioral options follow one pattern: a global default plus a per-calendar override. Per-event-type overrides apply only where §8.2 names them (duration, alarm, `class`, `transp`, description source). Rationale: users can learn two override layers. Users cannot learn an arbitrary cascade depth.

### 15.4 Deliberately not configurable

No setting exists for any of these: the attendee-write confirmation; the rule that URI actions land in drafts or confirms rather than server writes; the prohibition on auto-deleting server events from dangling pointers; round-trip preservation of unmodeled properties; the rule that validation gates pushes; the requirement that skips and failures surface. Rationale: each of these settings trades user safety or other people's data for convenience. A toggle is a promise to support both branches. The unsafe branch of each of these settings becomes a data-loss report or an email that nobody can unsend.

## 16. Integration

- `obsidian://davenport/...` URI actions (quick-add, open event, materialize). URI-triggered actions create drafts or open confirm modals. URI-triggered actions never write to a server directly. Rationale: URI handlers fire from any link that the user clicks.
- A public plugin API that exposes ledger queries and quick-add for other plugins.
- Importer for Full Calendar's note-per-event frontmatter format.
- ICS export of any calendar or filtered projection to a file.
- If the user drops an `.ics` file into the vault, Davenport offers to parse the file into a draft. Davenport offers no reply flow from a bare file. Davenport has no iMIP transport. Therefore a reply to an emailed invitation works only when the event already exists on a synced calendar through the server's scheduling inbox (§12).

## 17. Out of scope

This section states the exclusions, so that the borders are decisions:

- Google and Microsoft REST APIs (Google Calendar API, Google Tasks, Microsoft Graph). Davenport serves Google through its CalDAV endpoint (§4.4). Outlook.com has no CalDAV endpoint, and Davenport does not support Outlook.com.
- A shared OAuth client ID and the associated Google verification process. These two items are out of v1 scope. They are a v2 stretch goal (§4.4).
- A hosted auth proxy or any Davenport-operated server infrastructure.
- CardDAV/contacts sync. Person notes (§8.4) carry addresses in their own frontmatter. A future CardDAV integration would populate person notes and would not replace them. Such an integration could also share account configuration.
- VJOURNAL, VFREEBUSY/availability queries, and automatic scheduling (auto-placement of blocks into free time). Davenport defers these items. Davenport proposes, and the user disposes.
- Background sync and notifications on mobile. The mobile platform makes these two items impossible. The mitigations are the publish route (below) and the native client.
- Vault-as-server publishing (a secret-URL ICS feed of vault events through a companion relay). This feature is attractive and one-way. Davenport defers it to post-roadmap consideration.

## 18. Roadmap

Each stage is shippable:

1. ICS feed subscriptions → records, routing, materialization, templates. This stage exercises the whole read path with zero write risk.
2. CalDAV pull: discovery, registry, incremental sync, horizon, adoption/linking. The dirty set is the watcher plus self-write exclusion. The dirty set ships in this stage, so that the interim rule's dependency exists when the interim rule refers to it. Grace surfacing and push gating complete in stage 3. An interim rule applies to stages 2–3, before three-way comparison lands: Davenport defers and flags inbound changes to notes in the local dirty set. Davenport never applies such changes over dirty local state. The spec states this interim behavior here, so that nobody chooses the behavior silently at implementation time.
3. CalDAV push with the full trust surface: lifecycle, validation, quick-add, tombstones, round-trip patching, attendee gate, sync log, dry-run, pause. In this stage, a `412` surfaces as a blocking error on the item. The field-level resolution UI arrives in stage 4.
4. Conflict handling: three-way comparison, surfacing UI.
5. Tasks, VTODO targets, time blocks, transmutation and calendar moves (§10.4, decomposed design).
6. Google accounts: BYO-credential OAuth flow over CalDAV (§4.4).
7. Recurrence exceptions; RSVP; the description/attachment pipeline, if it did not land earlier.

Stretch (v2): shared OAuth client ID with Google verification (§4.4); vault-as-server publishing (§17).

26. WebDAV `MOVE` support per provider, and whether `MOVE` on scheduling-enabled collections stays silent to attendees. This item gates §10.4's atomic-move optimization only. No v1 behavior depends on it.
27. The type of each frontmatter value that Obsidian gives the plugin, in `metadataCache` and in the callback of `processFrontMatter`. The parser decides the type, and the YAML 1.1 family gives a date value for `2026-03-14` and for a time of day that states its seconds. The keys of §3.1 that state a day or a time of day are the keys where the type decides what the plugin can read. A date value holds one instant, and it does not hold the offset from universal time that the note states, so a date value cannot carry the resolution order of §3.1. Verify this item on the current Obsidian API version, and re-verify it at each Obsidian minor release. The reader admits a date value under a key of whole days and refuses one under a key that states a time of day, so no branch of this item changes the design. One residue rides the admitted path: a timestamp that the parser reduces to midnight in universal time reads as the day in universal time, and a negative offset makes that day differ from the day of the note. The item states which of the two paths real notes take, and the answer decides whether a real note reaches that residue.

## Appendix B — Lifecycle state table

This appendix enumerates the composed machine. The table has three axes: **note**, **record**, and **remote**. The **note** axis has five values. A plain note bears neither `uid` nor `state`. A plain note may also hold event-shaped fields, and acknowledgment produces exactly this kind of note (§5.6). These fields are inert in all cases: §5.3 does not watch them, and §6.1 does not render them. The fields stay inert until adoption (§6.3) or "Make this note an event" returns the note to the lifecycle. A draft note has `state: draft`. A ready note has `state: ready` and a `uid`. A bound note bears a `uid` and no `state`; the bound value is a frontmatter *shape*. A bound note is *live* only when a live record resolves for it (§3.1). The value none applies to a venue-routed record that has no 1:1 note. The **record** axis has five values: absent, live, tombstoned-L, tombstoned-R, and quarantined. A tombstoned-L record is local-intent. A tombstoned-R record is remote-observed. The **remote** axis has three values: absent, base, and changed. The remote has the value base when it matches the record's base snapshot. Each cell contains one of three things: a defined transition, a pointer to the governing section, or an explicit surface-to-user. A pointer is the preferred resolution. The best cell is an existing rule, not a new one.

### B.1 Named composite states

Two conditions recur often. Each condition has a name, and these names appear throughout:

- **Orphaned** — the note bears an identity whose record is tombstoned (either type). An orphaned note never pushes. Edits to it stay local-only, and its dirty entries stay inert. The note carries a banner, and the tombstone sets the banner type (retracted / cancelled remotely / converted, per annotation). Three resolutions apply. Acknowledgment strips `uid` and `state`, and the note becomes plain with its fields intact. Revival clears the orphan-era dirty entries, because "edits are local-only" must not later become a push (§5.6). A move suggestion (§5.6) is the third resolution.
- **Suspended** — the note bears an identity whose record is quarantined (§3.2). A suspended note never pushes, because it has no trustworthy base or etag. Its dirty entries accumulate. Its banner links to the quarantine item. On rebuild, the re-fetched base enters the normal §5.3/§5.4 evaluation. The accumulated dirty divergence then pushes (per mode, §4.2), or it conflicts as usual. A rebuild that gets a 404 follows row 16b: the note becomes orphaned, and the dirty entries go inert.
